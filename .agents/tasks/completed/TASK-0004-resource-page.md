## 2. INTENT

Bring the Java side of the `resource` bounded context into line with the six
migrations already written (`V128`–`V134`), then build the Resources list page
and the Create Resource page on the client.

The migrations exist and `V134` has already been run by the user against their
local database. The entities, DTOs and services still describe the *old* shape —
`resources.service_id` as a required single FK, `status` as a free-text
`VARCHAR`, `description`/`capacity`/`icon` as `NOT NULL`. Until the Java side
catches up, Hibernate's schema validation fails at boot (`missing column
[service_id] in table [resource.resources]`), so **the server does not currently
start**. Closing that gap is the first and blocking half of this task.

The second half builds the two client pages. The Stitch mocks
(`design/client/stitch/resources/screen.png`,
`design/client/stitch/create_resource/screen.png`) supply structure and layout
only. They were generated by an agent without architectural context and contain
fields this platform does not model at all — Section 5 lists exactly what to
drop and why. **Do not implement a mock field by inventing a column, a
`metadata` key, or a client-side-only concept to back it.**

This is **Phase 1 of 2**. Phase 1 makes the page functional against the data the
platform actually has. Every filter, search, sort and pagination control the
mock shows is rendered in Phase 1 as a **visibly reserved, inert control**, and
wired to real endpoints in Phase 2. Section 9.4 defines exactly what "reserved"
means here, and Section 5 forbids faking any of it client-side.

**Security is explicitly out of scope for this task** (Section 5). The user has
deferred the entire authorization tier — no `@PreAuthorize`, no policies, no
scope resolvers, no ownership checks beyond what already exists. Make it
functional; policies come later as their own task.

## 5. BOUNDARIES

- **Do not implement a mock field the schema cannot back.** The following
  appear in `create_resource/screen.png` and have no column, and the user has
  ruled each one out explicitly:
  - `LOCATION / ZONE` — no column, no domain concept.
  - `SERIAL NUMBER / ASSET ID` — no column; the user confirmed no serial/asset
    identifier exists anywhere in this platform's domains.
  - The entire `Availability & Scheduling` section, including
    `Always Available`, `PRE-BOOKING BUFFER (MIN)` and
    `POST-BOOKING CLEANUP (MIN)`. Buffers exist on `core.booking_policies`,
    **per service, not per resource**. Rendering them on a resource form would
    imply a per-resource scheduling model this platform does not have.

  Do not route any of these through `metadata` JSONB as a workaround.
  `CODING_CONVENTIONS.md` excludes `metadata` from DTOs, and using it to
  smuggle in unmodeled fields defeats the exclusion.
- **Do not fake filtering, search, sorting or pagination client-side.** No
  `Array.filter` over a full fetch, no client-side `slice()` pagination. A
  reserved control is disabled and inert; a control that appears to work by
  filtering an unpaginated payload is worse than one that is visibly off,
  because it silently breaks the moment the dataset outgrows one page.
- **Do not create a new service bean, orchestration component, or business
  flow.** New controller endpoints are explicitly permitted; new services are
  explicitly not. If a required endpoint appears to need logic no existing
  service method provides, that is a Section 13 escalation.
- Do not introduce a generic filter/specification/query-builder mechanism.
- Do not reintroduce `ResourceEntity.service` in any form.
- Do not add light-theme styles (`client/AGENTS.md`: dark only).
- Do not hand-edit `client/components/ui/` — the shadcn CLI owns it.

## 6. CONSTRAINTS

### Flyway — read before touching anything under `db/migration/`

- **`V134` has already been applied to the developer's local database.** The
  user ran it manually. `resource.resources.service_id` no longer exists there.
- **`V131__indexes_resource.sql` line 1 creates
  `idx_resources_service_id ON resource.resources(service_id)` — an index on
  the column `V134` drops.** Sequentially this is harmless (Postgres drops a
  dependent index with its column), but the line is now dead.
  **Determine whether `V131` has already been applied before deciding what to
  do:**
  ```sql
  SELECT version, success FROM flyway_schema_history WHERE version = '131';
  ```
  - Already applied → **do not edit `V131`.** Editing an applied migration
    changes its checksum and Flyway's `validate` fails the next boot. Leave the
    dead line; note it in the closing report.
  - Not yet applied → removing that one line is permitted and preferable.
  - Cannot determine → escalate (Section 13). Do not guess.
- No new migration is required by this task. If you believe one is, that is an
  escalation, not a decision to make silently.
- `SERVER_AGENTS.md` records the applied high-water mark as **v125**; `V126`
  through `V134` now exist in the tree. Any new migration must be `V135+`.
  Never renumber below the high-water mark — that failure mode is documented
  in `SERVER_AGENTS.md` and cost a previous session a full debugging cycle.
- `database/init/resource/` uses **different numbers** from the Flyway tree
  (`V50`–`V57` there vs `V34`–`V41` here). Mirrors continue the `database/init`
  sequence; they do not copy Flyway's numbers. Flyway copies carry **zero
  comments**; `database/init` copies carry the explanatory ones.

### Architectural

- `resource_services` is a **pure composite-PK join table**. `V128` declares
  `PRIMARY KEY (resource_id, service_id)` with **no surrogate `id`**.
  This is the single most important structural detail in the task, and it is
  where "do it exactly like `resource_assignments`" must be read carefully:
  copy `resource_assignments`' **package layout, file naming, and CRUD
  conventions**, but **not** its surrogate-PK identity strategy —
  `ResourceAssignmentEntity` has `id BIGSERIAL PRIMARY KEY`, this table does
  not. The correct identity precedents are `ResourceAttributesEntity`
  (`resource/attribute/`, with its `id/ResourceAttributesId` folder) and
  `UserRoleEntity` / `MembershipRoleEntity`. Concretely:
  - `@EmbeddedId ResourceServiceId` in a `resourceservice/id/` folder.
  - `JpaRepository<ResourceServiceEntity, ResourceServiceId>`.
  - `findById`/`existsById`/`delete` take a constructed
    `new ResourceServiceId(resourceId, serviceId)`.
  - Controller exposes the key as two path segments:
    `/{resourceId}/{serviceId}`.
  - **No `update` verb.** The table is its composite key plus an immutable
    `@CreationTimestamp created_at` — there is no mutable attribute to update.
    This is the established `UserRole`/`RolePermission`/`MembershipRole`
    precedent, and `CODING_CONVENTIONS.md` states it directly: omit a verb the
    entity's shape does not support rather than implementing a no-op.
  - **A `existsById` duplicate check before create is mandatory**, not
    optional: `JpaRepository.save()` on a non-null composite `@Id` performs a
    silent `merge` (UPDATE), not an INSERT-or-fail, so without the guard a
    duplicate "create" quietly succeeds. Throw
    `DuplicateResourceServiceException` → 409.
- Native enum wiring follows `BookingEntity.status` exactly:
  `@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`.
  **Unlike `BookingEntity`, do not add `@Builder.Default`** —
  `resource.resources.status` has no SQL `DEFAULT` (`V35` declared it
  `NOT NULL` with no default and `V130` only changed the type). It therefore
  stays a required field: `@NotNull` on the request, no guarded-optional
  treatment. Getting this backwards produces rows that silently default
  instead of failing validation.
- All new DTO fields follow `CODING_CONVENTIONS.md`: `Request` excludes PK/UID/
  timestamp columns; `Response` flattens every FK to its raw scalar id;
  `metadata` stays excluded from both.
- Controllers keep returning bare DTOs with class-level status annotations,
  matching every existing controller. The known `ResponseEntity` deviation
  recorded in `SERVER_AGENTS.md` is **not** reconciled here.

### Client

- The browser never calls Spring directly. Every call goes
  browser → `bffClient` → Next Route Handler → `platformClient()` → Spring.
- Never import `lib/env.ts`'s `serverEnv()`, `lib/session.ts`, or any
  `*-gateway.ts` into a Client Component.
- Route handlers must not return tokens in a response body.
- Every redirect to `/login` uses `SESSION_EXPIRED_REDIRECT` from
  `lib/auth-cookies.ts`, never a bare `redirect("/login")` — the redirect-loop
  invariant in `client/AGENTS.md` is non-negotiable and has already shipped
  broken once.
- Every authenticated platform call goes through `withAccessToken`, with
  `allowSessionWrite: false` from Server Components.
- Every dynamic `className` composes through `cn()`; static ones stay plain
  strings.
- Tailwind v4, zod v4 (`z.email()`, `{ error: "..." }`), shadcn `base-nova` on
  Base UI — `Checkbox`/`Select` need a react-hook-form `<Controller>`, not
  `register()`.
- Use semantic tokens (`bg-surface`, `text-muted-foreground`, `border-border`)
  and the 4px spacing scale. No raw hex.

## 9. FUNCTIONAL REQUIREMENTS

### 9.1 Entity & DTO alignment

1. `ResourceStatus` exists at `resource/enums/ResourceStatus.java` with exactly
   `ACTIVE`, `INACTIVE`, `MAINTENANCE`, `RETIRED`, in that order (matching
   `V130`).
2. `ResourceEntity.status` is typed `ResourceStatus`, annotated
   `@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`,
   `nullable = false`, **no** `@Builder.Default`.
3. `ResourceEntity.description` and `ResourceEntity.capacity` no longer declare
   `nullable = false`. `ResourceTypeEntity.icon` no longer declares
   `nullable = false`.
4. `ResourceRequest`: `description` loses `@NotBlank`; `capacity` loses
   `@NotNull`; `status` is typed `ResourceStatus` and keeps `@NotNull` (losing
   `@NotBlank`/`@Size`, which are `String`-only); `serviceId` is removed
   entirely.
5. `ResourceTypeRequest.icon` loses `@NotBlank` and keeps `@Size(max = 100)`.
6. `ResourceResponse`: `serviceId` removed; `status` typed `ResourceStatus`.
7. `ResourceEntity` has no `service` field and no `ServiceEntity` import.
   `ResourceServiceImpl` no longer injects `ServiceRepository` and no longer
   references `ServiceNotFoundException` — unless the new `resourceservice`
   domain is the only remaining user, in which case that injection moves there.

### 9.2 `resource_services` domain

8. `ResourceServiceEntity` maps `resource.resource_services` with
   `@EmbeddedId ResourceServiceId(resourceId, serviceId)`, two `@MapsId`
   `@ManyToOne` associations, and a `@CreationTimestamp createdAt`.
9. Full CRUD **minus `update`**: create, get-by-composite-id, list, delete.
10. `create` performs `existsById` before building and throws
    `DuplicateResourceServiceException` (409) on a hit.
11. `create` resolves both sides via their real repositories, throwing
    `ResourceNotFoundException` / `ServiceNotFoundException` on a miss.
12. `ResourceServiceNotFoundException` (404) and
    `DuplicateResourceServiceException` (409) are both registered in
    `GlobalExceptionHandler` using the existing `ApiErrorResponse` shape.
13. `GET /api/v1/resource-services?resourceId={id}` returns every service link
    for one resource.

### 9.3 Resources list page — functional in Phase 1

14. `/dashboard/resources` renders every resource in the caller's organization:
    name, type name, capacity, status, and assigned service names.
15. `capacity == null` renders as `N/A` (the mock's own projector row shows
    this) — not `0`, not blank.
16. `status` renders as a labelled badge, one visual treatment per
    `ResourceStatus` value. `MAINTENANCE` is a warning treatment, not an error
    one; `RETIRED` is neutral/muted, not destructive.
17. Empty state mirrors `ServiceCatalogList`'s dashed-border treatment.
18. Load failure renders an inline error and **keeps the session** — only
    `SessionExpiredError` redirects, and only via `SESSION_EXPIRED_REDIRECT`.
19. A "Create Resource" link routes to `/dashboard/resources/new`.

### 9.4 Reserved (Phase 2) — rendered, visibly inert

20. Type filter, status filter, "More Filters", the search input, and the
    pagination control are all rendered and all `disabled`.
21. Each carries a code comment naming the exact Phase 2 endpoint that will
    activate it (Section 14 Step 12 lists them).
22. Each is visually distinguishable as unavailable — not merely
    non-responsive. A user must not be able to mistake a reserved control for
    a broken one.
23. The three stat tiles (Total Resources / Active Assets / Utilization Rate)
    are **reserved in full**. "Utilization" depends on booking data that has no
    endpoint and no query behind it. Do not compute a number from the loaded
    page — a plausible-looking wrong statistic is materially worse than a
    visibly pending one.

### 9.5 Create Resource page — functional in Phase 1

24. Fields, in this order, per the user's explicit layout instruction:
    **Basic Information** → Resource Name → Description → **Resource Type
    (last)**. Then **Specifications** → Capacity → Status.
    The description-above-type ordering and type-last-in-section placement are
    a deliberate change from the mock, requested directly.
25. Resource Type is a `<Select>` populated from
    `GET /api/v1/resource-types?organizationId=`.
26. The type control handles the **empty case explicitly**: a new organization
    has zero resource types, and `resources.resource_type_id` is `NOT NULL`, so
    the form is unsubmittable until one exists. Render an explanatory empty
    state with a route to create a type. Do **not** silently render an empty

## 13. ESCALATION

Stop and report rather than deciding, if any of these occur:

1. **`V131`'s applied state cannot be determined** (Section 6). Editing an
   applied migration breaks Flyway validation and the server will not boot.
   Never guess.
2. **A migration and this document disagree** about a column's type,
   nullability, or presence. The migration is authoritative; report the
   discrepancy rather than "fixing" either side.
3. **`ServerApplicationTests.contextLoads()` still fails after the entity
   changes** with a *different* schema-validation error. That means the local
   database has drifted from the migration tree in some way this task did not
   anticipate — report the exact error, do not start hand-patching the database
   or adding migrations to paper over it.
4. **An endpoint the client needs appears to require business logic no existing
   service method provides.** Section 5 forbids new services. Report the gap
   with the specific requirement rather than quietly adding a service.
5. **A mock field seems genuinely necessary** despite Section 5's exclusion
   list. Report it; do not model it, and do not smuggle it through `metadata`.
6. **Deleting the two list endpoints (Deliverable 5) turns out to break a
   caller** not identified here. Report the caller.
7. **Any authorization question at all.** The security tier is deferred by
   explicit decision. If something looks exploitable, note it in the closing
   report — do not fix it, and do not let it expand this task's scope.
8. Anything that would require touching `auth/`, `security/`, `core/service/`,
   or `organization/`.

Do not silently resolve architectural or security ambiguity. A wrong guess that
compiles is more expensive here than a question.

## 14. IMPLEMENTATION PLAN

### Phase A — unblock the boot (Steps 1-5)

Nothing else can be verified until `contextLoads()` passes, because the server
will not start. Do these first, in order, and run Validation #1 after Step 5.

**Step 1 — `ResourceStatus`.**
Create `resource/enums/ResourceStatus.java` with the four constants. File shape
copies `core/enums/BookingStatus.java`.

**Step 2 — Wire the enum onto `ResourceEntity`.**
Replace `private String status` with `private ResourceStatus status`, annotated
`@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)` +
`@Column(name = "status", nullable = false)`. Drop the `length = 50`, which is
meaningless for a native enum. **No `@Builder.Default`** — add a short comment
saying why, since every sibling status column in this codebase has one and its
absence here will otherwise read as an oversight.

**Step 3 — Relax nullability.**
`ResourceEntity`: remove `nullable = false` from `description` and `capacity`.
`ResourceTypeEntity`: remove it from `icon`. Three annotation edits, no other
changes.

**Step 4 — Drop `ResourceEntity.service`.**
Delete the field, its `@ManyToOne`/`@JoinColumn`, and the `ServiceEntity`
import. Then follow the compiler: `ResourceRequest.serviceId`,
`ResourceResponse.serviceId`, and every `service`-related line in
`ResourceServiceImpl` (`ServiceRepository` injection, both `findById` lookups,
`.service(...)` on the builder, `setService(...)` on update). Let
`compileJava` enumerate the call sites rather than grepping by hand.

**Step 5 — Align the DTOs.**
`ResourceRequest`: `status` becomes `@NotNull ResourceStatus`; `description`
loses `@NotBlank`; `capacity` loses `@NotNull`.
`ResourceResponse`: `status` becomes `ResourceStatus`.
`ResourceTypeRequest`: `icon` loses `@NotBlank`, keeps `@Size(max = 100)`.

▶ **Run Validation #1 now.** `contextLoads()` must pass before continuing. If
it fails with a *different* schema error, that is Escalation #3.

### Phase B — the `resource_services` domain (Steps 6-8)

**Step 6 — Build the domain.** Package
`resource/resourceservice/`, mirroring `resource/assignment/`'s layout:
```
resourceservice/
  id/ResourceServiceId.java              @Embeddable, (resourceId, serviceId)
  entity/ResourceServiceEntity.java      @EmbeddedId + 2 @MapsId @ManyToOne
  repository/ResourceServiceRepository.java
  dto/ResourceServiceRequest.java        resourceId, serviceId (both @NotNull)
  dto/ResourceServiceResponse.java       resourceId, serviceId, createdAt
  exception/ResourceServiceNotFoundException.java
  exception/DuplicateResourceServiceException.java
  service/ResourceServiceService.java
  service/impl/ResourceServiceServiceImpl.java
  controller/ResourceServiceController.java
```
Naming note: `ResourceServiceService`/`ResourceServiceServiceImpl` reads
awkwardly but is correct — the domain noun is "resource service", and the
suffix is the layer. The alternative (`ResourceServiceImpl`) **already exists**
in `resource/resources/service/impl/` and would collide. This is the same
collision that forced `OrganizationServiceService` → `BusinessServiceService`
earlier; do not repeat it by picking the short name.

`ResourceServiceId` implements `Serializable` and provides `equals`/`hashCode`
— required for `@EmbeddedId`. Copy `ResourceAttributesId`.

Repository: `JpaRepository<ResourceServiceEntity, ResourceServiceId>` plus
`List<ResourceServiceEntity> findByResourceResourceId(BigInteger resourceId)`
and `List<ResourceServiceEntity> findByServiceServiceId(BigInteger serviceId)`.

Impl: `create` → `existsById` guard (comment *why*: silent merge) → resolve
both FKs via their repositories → build → save. `getById(resourceId,
serviceId)`, `getAll`/`getByResourceId`, `delete(resourceId, serviceId)`.
**No `update`.**

Controller: `@RequestMapping("/api/v1/resource-services")`, `POST`,
`GET /{resourceId}/{serviceId}`, `GET` with optional `?resourceId=`,
`DELETE /{resourceId}/{serviceId}`.

**Step 7 — Register both exceptions** in `GlobalExceptionHandler`, copying an
adjacent handler pair verbatim (404 / 409, `ApiErrorResponse`).

**Step 8 — Compile and run Validations #5 and #6.**

## 15. REVIEW STRATEGY

### What to review

1. **Migration ↔ entity correspondence.** Read all six migrations side by side
   with `ResourceEntity` and `ResourceTypeEntity`. Every column's nullability,
   type and name must match. This is the highest-value check in the review;
   `contextLoads()` catches most of it but not, for example, a nullable column
   left `@NotNull` in the DTO.
2. **The composite-PK entity.** Confirm `@EmbeddedId` (not a surrogate `id`),
   `@MapsId` on both associations, `Serializable` + `equals`/`hashCode` on the
   id class, `JpaRepository<_, ResourceServiceId>`, and **no `update` verb**.
   Then confirm the `existsById` guard exists in `create` — its absence is
   silent data loss, not a visible bug, and Validation #5 is the only thing
   that surfaces it.
3. **`@Builder.Default` on `status`.** Must be **absent**. Present is a real
   defect: it lets an unspecified status silently become a value instead of
   failing validation.
4. **No new service beans.** `git diff --stat` over `server/` should show
   exactly one new `@Service` (`ResourceServiceServiceImpl`) and no new file
   under `service/`.
5. **Reserved controls are genuinely inert.** Grep the client diff for
   `.filter(`, `.slice(`, `.sort(` over resource arrays. Any hit is a Section 5
   violation.
6. **Comment quality** against
   `.skills/workflows/quality-code-comments/SKILL.md`. Expect roughly three
   comments in the backend diff. Many more means restatement crept in; zero
   means the two non-obvious decisions (no `@Builder.Default`, the
   `existsById` guard) went undocumented.
7. **Client invariants:** no bare `redirect("/login")`; `allowSessionWrite:
   false` in Server Components; no gateway import in a Client Component; `cn()`
   on dynamic classNames only.

- Run `.skills/workflows/code-review/SKILL.md` over the full diff.

  reported — #5 in particular cannot be caught by reading.
- Read the closing report against Section 4's out-of-scope list. Anything fixed
  that Section 4 said to leave alone is scope creep and should be raised even
  though the change may look like an improvement.
