## 2. INTENT

Replace `app/dashboard/page.tsx` — currently a session-debug card showing actor
type, subject and tenant — with the real dashboard home: a title, today's date,
a row of metric tiles, and a table of the ten latest bookings.

Serve all of it from **one** new orchestration endpoint,
`GET /api/v1/dashboard/summary`, so the page costs one platform round trip
instead of the six-request fan-out the bookings page currently performs.

### The mock is a sketch, not a specification

`design/client/stitch/dashboard/screen.png` was generated by an agent without
architectural context. It is authoritative for **nothing**. The task author has
already reduced it to what the platform can honestly answer, and §5 records
every element that was cut and why.

What survives, and it is the whole page:

1. `Dashboard` title.
2. Today's date beneath it.
3. A row of metric tiles.
4. A table of the ten latest bookings, `start_time` descending.

Everything else in that mock — the export/customize buttons, the active-location
count, the Google-Calendar-style resource timeline, the Requires Action column,
the Recent Activity Feed and the Infrastructure Status panel — is **deleted from
the design**, not deferred and not reserved. Do not build any of it, and do not
leave a placeholder where one used to be.

### The revenue problem, stated once so it is not rediscovered

`core.bookings` has **no amount and no currency column** — only
`paid BOOLEAN`. `core.services.min_price` / `max_price` are a nullable
*advertised range*, not a charged amount. The `billing` schema is explicitly
excluded from PLATFORM V1.0.0 (`AGENTS.md` → "Platform Stage").

There is therefore no honest revenue figure to compute. The tile ships
**visibly reserved with no number at all**, and — this is the load-bearing half
— the server response carries **no revenue field whatsoever**, not even a null
one. A nullable `revenue` on the wire is an invitation for the next contributor
to fill it with `SUM(min_price)`, which would look authoritative while measuring
nothing. Adding a price column is Escalation #1.

## 9. FUNCTIONAL REQUIREMENTS

### 9.1 The endpoint

```
GET /api/v1/dashboard/summary?organizationId={id}     (required)
-> 200 DashboardSummaryResponse
```

- `organizationId` is **required**. Omitting it is a 400 from Spring's own
  missing-parameter handling — there is no unscoped fallback and no "everything"
  form, matching the post-`TASK-0005` rule for `/bookings`, `/attendees` and
  `/booking-resources`.
- **No `Pageable`, no `?sort=`, no `?size=`, no `?tab=`, no date parameter.**
  The payload shape is fixed. A dashboard that can be re-sorted by query string
  is the bookings page, and it already exists. Adding any of these is a review
  finding.
- An organization with no bookings returns `200` with zeroed metrics and an
  empty `recentBookings` array — **never** a 404. An unknown `organizationId`
  behaves identically. This mirrors `getResourceStatsByOrganizationId`'s
  all-zero-on-mismatch precedent; the endpoint must not become an existence
  oracle for organization ids.

```json
{
  "organizationId": 12,
  "timezone": "Australia/Sydney",
  "date": "2026-09-09",
  "metrics": {
    "todaysBookings": 14,
    "pending": 3,
    "cancellations": 2
  },
  "recentBookings": [
    {
      "bookingId": 812,
      "bookingUid": "0f3c8a91-...",
      "title": "Product Photography",
      "startTime": "2026-09-09T01:00:00Z",
      "endTime": "2026-09-09T02:30:00Z",
      "status": "ACCEPTED",
      "serviceId": 4,
      "serviceTitle": "Studio Hire",
      "customerName": "Sarah Jenkins",
      "resourceName": "Studio A"
    }
  ]
}
```

Three DTOs, all records, all in `service/dashboard/dto/`:

```
DashboardSummaryResponse(BigInteger organizationId, String timezone,
                         LocalDate date, DashboardMetricsResponse metrics,
                         List<DashboardBookingRowResponse> recentBookings)
DashboardMetricsResponse(long todaysBookings, long pending, long cancellations)
DashboardBookingRowResponse(BigInteger bookingId, UUID bookingUid, String title,
                            Instant startTime, Instant endTime,
                            BookingStatus status, BigInteger serviceId,
                            String serviceTitle, String customerName,
                            String resourceName)
```

- **No `revenue` field on `DashboardMetricsResponse`**, not even nullable (§2).
  Put the reason in the record's Javadoc, in the style of
  `ResourceStatsResponse`.
- `customerName` and `resourceName` are **nullable** — a booking may have no
  attendee and no primary resource. Serialize them as `null`; the client renders
  `—`.
- These are response-only DTOs. There is no request DTO, no `@Valid`, and no
  `Request` record in this task.

### 9.2 Metric definitions — exact predicates

Let `dayStart` / `dayEnd` be the org-local day window from §9.3. All three
counts are additionally constrained by
`BookingSpecifications.hasOrganization(organizationId)`.

| Metric | Predicate | Why this shape |
|---|---|---|
| `todaysBookings` | `startTime >= dayStart AND startTime < dayEnd` AND `status IN (PENDING, ACCEPTED, AWAITING_HOST)` | "What is happening today" — cancelled work is not happening. Deliberately consistent with `BookingTab.UPCOMING`'s status set so the tile and the list never disagree about what a live booking is. |
| `pending` | `status IN (PENDING, AWAITING_HOST)` — **no time window** | A work queue, not a daily statistic. An overdue request still needs answering, which is exactly the reasoning already baked into `BookingTab.PENDING`. |
| `cancellations` | `startTime >= dayStart AND startTime < dayEnd` AND `status IN (CANCELLED, REJECTED)` | Both terminal negatives, one number — same pairing as `BookingTab.CANCELLED`. |

Four consequences that are easy to get wrong:

1. **`pending` intentionally has no window while the other two do.** That
   asymmetry is the specification, not an oversight. Give it a `why` comment so
   the next reader does not "fix" it.
2. **`cancellations` is scoped by the booking's start day, not by when it was
   cancelled.** `core.bookings` has no `cancelled_at` column, so "cancelled
   today" is not computable. The tile means *"of today's bookings, N are
   cancelled"*. The client label must not claim otherwise, and the DTO Javadoc
   must say so.
3. **`todaysBookings` and `cancellations` are disjoint**, and neither is the
   total. `todaysBookings + cancellations` is every booking starting today. Do
   not present either as a percentage of the other — the mock's `3.2%` rate is
   deleted (§5).
4. **The window is half-open**, `[dayStart, dayEnd)`. A booking starting at
   exactly midnight tomorrow belongs to tomorrow. Use `lessThan`, never
   `lessThanOrEqualTo`.

Each count is one `bookingRepository.count(specification)` call. Three counts,
three queries. Do not fetch rows to count them, and do not compute any of these
in Java from a fetched list.

### 9.3 The day window and the timezone

```java
ZoneId zone = resolveZone(organization.getTimezone());
LocalDate today = LocalDate.now(zone);
Instant dayStart = today.atStartOfDay(zone).toInstant();
Instant dayEnd = today.plusDays(1).atStartOfDay(zone).toInstant();
```

- **Resolve the day server-side, in the organization's timezone**, and return
  both `date` and `timezone` on the payload. The client renders the date it is
  given and never calls `new Date()` for it — a Server Component computing
  "today" from the server's own clock while the browser computes it from the
  user's is a hydration mismatch, and one that only misfires near midnight,
  which is the worst possible time to debug it.
- Use `LocalDate.atStartOfDay(ZoneId)`, **not** `atStartOfDay().atZone(zone)`.
  The former resolves DST gaps correctly; the latter silently produces the wrong
  instant on a spring-forward day.
- **`organization.timezone` is an unvalidated `VARCHAR(100)`**, so `ZoneId.of`
  can throw `DateTimeException` on stored garbage. `resolveZone` catches it and
  falls back to `ZoneOffset.UTC` with a `why` comment. A dashboard that 500s
  because someone typed `Australia/Sidney` is worse than one whose day boundary
  is a few hours off.
- **Capture `LocalDate.now(zone)` exactly once** in the service method and pass
  the resulting `Instant`s into every specification. Do not call `Instant.now()`
  or `LocalDate.now()` inside a `Specification` lambda: the lambda is evaluated
  once per query, and three counts evaluated at three different instants can
  return a set of numbers that never simultaneously described reality. This is
  the same trap `TASK-0005` §10.3 documented for count-vs-content on a page.
- The organization is loaded once via `OrganizationRepository.findById`. If it
  is absent, fall back to UTC and continue with zeroed metrics — do **not**
  throw `OrganizationNotFoundException` (§9.1's no-oracle rule).

### 9.4 The ten latest bookings — and the N+1 rules

```java
private static final int RECENT_BOOKING_LIMIT = 10;

Pageable pageable = PageRequest.of(
    0, RECENT_BOOKING_LIMIT, Sort.by(Sort.Direction.DESC, "startTime"));

List<BookingEntity> recent = bookingRepository
    .findAll(BookingSpecifications.hasOrganization(organizationId), pageable)
    .getContent();
```

- **No status filter.** "Ten latest bookings" means all of them, cancelled
  included — equivalent to `BookingTab.ALL`. The status badge is what
  distinguishes them.
- `startTime` **descending**, as specified by the task author. Note that this
  puts the furthest-future booking first, so the next thing happening is at the
  bottom. `TASK-0005` raised the same point about the bookings list and the
  author kept DESC. **Implement DESC. Do not switch it.** It may be raised again
  in the closing report; it may not be changed in the code.
- Construct the `PageRequest` **inside the service**. Do not accept a `Pageable`
  parameter and do not route it through `BookingSort.sanitize` — there is no
  client-supplied sort on this endpoint for a whitelist to protect.

**Enrichment — this is the part most likely to be got wrong.**

After the ten rows are in hand, collect their ids **once** and issue exactly two
batched queries:

```java
List<BigInteger> bookingIds = recent.stream().map(BookingEntity::getBookingId).toList();
// guard: an empty IN () list is invalid SQL on some dialects — return early
List<AttendeeEntity> attendees =
    attendeeRepository.findByBookingBookingIdIn(bookingIds);
List<BookingResourceEntity> primaries =
    bookingResourceRepository.findByBookingBookingIdInAndIsPrimaryTrue(bookingIds);
```

then build `Map<BigInteger, …>` lookups and join in memory.

- **Never one query per row.** A loop calling
  `findByBookingBookingIdAndIsPrimaryTrue(id)` ten times is a task failure, not
  a style preference — see `.skills/workflows/performance-avoid-quadratic/`.
- **Never fetch the whole organization's attendees.**
  `findByBookingServiceOrganizationOrganizationId` exists and is what the
  bookings gateway uses; it grows without bound with booking history. Ten ids
  is the correct scope here. Reusing the org-wide finder is a review finding.
- **Guard the empty list.** With no bookings, skip both queries and return an
  empty `recentBookings` immediately.
- `customerName` is the attendee with the **lowest `attendeeId`** for that
  booking — deterministic, and the same "first attendee" rule the bookings table
  already uses. Extra attendees are not surfaced on the dashboard. `null` when
  there are none.
- `resourceName` comes from the primary link's `resource.name`. `uq_booking_resources_primary`
  guarantees at most one, so no tie-break is needed. `null` when there is none.
- `serviceTitle` comes from `booking.getService().getTitle()`.

**Transaction boundary.** Every association on `BookingEntity` is
`FetchType.LAZY`, so the service method **must** be annotated
`@Transactional(readOnly = true)` and must map entities to DTOs *inside* that
method. Returning entities and touching `.getService()` in the controller works
today only because open-session-in-view is on by default; that is an accident,
not a contract, and it breaks silently with `LazyInitializationException` the
day someone disables it.

**Accepted cost, to be stated in the closing report rather than optimized away
here:** `getService().getTitle()` and `getResource().getName()` each trigger a
lazy load per distinct association, bounded at ten rows. That is acceptable at
this fixed limit. Do **not** add an `@EntityGraph`, a `@Query` with `JOIN FETCH`,
or a projection interface to avoid it — that is scope this task did not buy, and
`BookingRepository` is out of scope (§4). Report the count; do not change it.
