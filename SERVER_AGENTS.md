*Note everything important about the server in here*

# Stack

- Java 21, Spring Boot 4.1, Gradle Kotlin DSL (`server/build.gradle.kts`)
- Jackson 3 — import from `tools.jackson.databind.*`, NOT `com.fasterxml.jackson.*`
- Hibernate ORM via `spring-boot-starter-data-jpa`, Jakarta Persistence (`jakarta.persistence.*`)
- Flyway (`flyway-database-postgresql`) owns the schema. Hibernate `ddl-auto` is never used to generate/alter schema — entities are written to match existing `V*__*.sql` migrations exactly, never the other way around.
- No extra ORM libraries (e.g. no hypersistence-utils) — native Postgres enum/JSON mapping is done with plain Hibernate 6.2+ annotations (see below).

# Migrations

- Authored with comments in `database/init/<domain>/`, then mirrored comment-free into `server/src/main/resources/db/migration/<domain>/` on request.
- SQL conventions: `BIGSERIAL` PKs, named FK/index constraints, single-line FK/index formatting, zero comments in the Flyway copy.

# Package structure

Domain-driven, one folder per subdomain under its bounded context, each with `entity/`, `repository/`, `service/`, `controller/`, `dto/` (created as needed, not all populated upfront):

```
auth/
  user/, role/, permission/, account/, apikey/, attribute/,
  password/, refreshtoken/, rolepermission/, session/, userrole/
  enums/          <- auth-schema-specific enums (e.g. AccountStatus)
global/
  enums/          <- cross-schema/public-schema enums (Locale, Theme, WeekStart, Currency)
  exception/, handler/, response/, utils/
security/
  authorization/, config/, identity/, oauth/, permission/, policy/, token/
```

Other top-level bounded contexts mirror the schemas: `analytics`, `audit`, `billing`, `core`, `customer`, `feature` (appointment/auth/notification/slot/workspace), `integration`, `notification`, `organization`, `resource`, `tenant`, `webhook`, `widget`.

`tenant/` subdomains observed so far: `tenants/`, `ecosystem/`, `plan/`, `domain/`, `enums/` (`TenantStatus`, `TenantRegion`, `EcosystemStatus` — all `tenant`-schema-scoped native Postgres enums).

`organization/` subdomains observed so far: `organizations/`, `profile/`, `membership/`, `membershiprole/` (all four now implemented). `membershiprole/` also has an `id/` folder for its `@EmbeddedId` class — see composite-key note below.

`widget/` subdomains observed so far: `widgets/`, `widgetorigin/`, `enums/` (`WidgetStatus`, `WidgetType` — `widget`-schema-scoped native Postgres enums).

`core/` subdomains observed so far: `schedule/`, `attendee/`, `booking/`, `outofoffice/`, `availability/`, `service/`, `bookingpolicy/`, `selectedslot/`, `enums/` — all now implemented (`ScheduleEntity`, `AvailabilityEntity`, `ServiceEntity`, `BookingEntity`, `BookingPolicyEntity`, `AttendeeEntity`, `SelectedSlotEntity`, `OutOfOfficeEntity`), completing the `core` bounded context. `core/enums/` has `BookingMode` and `BookingStatus`, both wired up as the native-enum-backed `core.booking_mode`/`core.booking_status` Postgres types on `BookingPolicyEntity.bookingMode`/`BookingEntity.status` respectively (unused by `ServiceEntity` — its `period_type` is a plain `VARCHAR`, not a native enum; see below).

`integration/` subdomains observed so far: `calendar/`, `sheets/`, `enums/` (`IntegrationType` — `integration`-schema-scoped native Postgres enum, shared by both `destination_calendars` and `destination_sheets`).

`resource/` subdomains — all now implemented: `type/` (`ResourceTypeEntity`), `resources/` (`ResourceEntity`), `pricing/` (`ResourcePricingEntity`), `assignment/` (`ResourceAssignmentEntity`), `calendar/` (`ResourceCalendarEntity`), `maintenance/` (`ResourceMaintenanceEntity`), `attribute/` (`ResourceAttributesEntity`, plus an `id/` folder for its `@EmbeddedId` class — see composite-key note below), `overrides/` (`ResourceOverrideEntity`). `assignment/` briefly had its own `id/` folder with a `ResourceAssignmentId` `@EmbeddedId` stub, deleted once the migration showed it didn't fit a composite key — see the `ResourceAssignmentEntity` note below.

# Entity conventions

Established across `UserEntity`, `RoleEntity`, `PermissionEntity`, `AccountEntity`, `ApiKeyEntity`, `RefreshTokenEntity`, `TenantEntity`, `EcosystemEntity`, `TenantPlanEntity`, `TenantDomainEntity`, `OrganizationEntity`, `MembershipEntity`, `ProfileEntity`, `MembershipRoleEntity`, `WidgetEntity`, `WidgetOriginEntity`, `UserPasswordEntity`, `UserRoleEntity`, `RolePermissionEntity`:

- **PK**: `BigInteger` field named `<entityClassName minus "Entity">Id` (e.g. `userId`, `roleId`, `permissionId`), mapped to DB column `id`, via `@GeneratedValue(strategy = GenerationType.IDENTITY)` — matches `BIGSERIAL`. The PK name follows the **class name**, not the folder/table name: `tenant.plans` lives under package `tenant/plan/` but the class is `TenantPlanEntity` (disambiguating from a bare `PlanEntity`), so its PK is `tenantPlanId`, not `planId`. Same pattern for `tenant.tenant_domains` under package `tenant/domain/` — class `TenantDomainEntity`, PK `tenantDomainId`, not `domainId`.
- **Timestamps**: `Instant createdAt` / `Instant updatedAt` via `@CreationTimestamp` / `@UpdateTimestamp` (`org.hibernate.annotations`) — matches `TIMESTAMPTZ ... DEFAULT now()`. `createdAt` is `updatable = false`. `Instant` (not `OffsetDateTime`) is the standard choice, matching the platform's canonical-UTC temporal architecture goal.
- **UUID columns** (e.g. `users.uid`): `@UuidGenerator` (`org.hibernate.annotations.UuidGenerator`), `nullable = false, unique = true, updatable = false`. Hibernate generates the UUID client-side; the DB's `gen_random_uuid()` default is not relied on.
- **Postgres native enum columns** (e.g. `public.locale`, `public.theme`, `public.week_start`, `auth.account_status`): map to a Java enum with `@Enumerated(EnumType.STRING)` + `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`. No extra dependency needed — this is native Hibernate 6.2+ support.
- **JSONB columns**: map to `tools.jackson.databind.JsonNode` via `@JdbcTypeCode(SqlTypes.JSON)`.
- **Native Postgres array columns** (e.g. `core.availabilities.days INTEGER[]`): map to the boxed array type (`Integer[]`, not `int[]` or `List<Integer>`) via `@JdbcTypeCode(SqlTypes.ARRAY)` (`org.hibernate.annotations.JdbcTypeCode` / `org.hibernate.type.SqlTypes`) — same annotation family as the JSONB pattern, just a different `SqlTypes` constant. First observed on `AvailabilityEntity.days`.
- **Enum placement**: enums scoped to one Postgres schema and reused only within that schema's tables live in `<schema>/enums/` (e.g. `auth/enums/AccountStatus.java`). Enums under the `public` Postgres schema, shared across domains, live in `global/enums/` (`Locale`, `Theme`, `WeekStart`, `Currency`).
- **Lombok**: `@NoArgsConstructor`, `@AllArgsConstructor`, `@Builder` on every entity. `RoleEntity`/`PermissionEntity`/`AccountEntity` also carry `@Getter`/`@Setter`; `UserEntity` currently does not — flagged here as an observed inconsistency, not a deliberate rule, in case it should be reconciled later.
- Columns with a SQL `DEFAULT` that Hibernate doesn't auto-populate (e.g. plain non-generated NOT NULL columns like `locale`, `theme`, `week_start`, `account_status`, `timezone`) should mirror the DB default as a `@Builder.Default` literal, so entities built via the Lombok builder without setting them don't send an explicit `NULL` that would shadow the DB default and violate `NOT NULL`.
- **Not every table has `created_at`/`updated_at`** — e.g. `auth.accounts` (OAuth provider linkage) has neither; don't add timestamp fields unless the migration actually declares those columns.
- **FK to a schema/entity that doesn't exist yet**: map the raw column as a plain `BigInteger` field (not a relationship) instead of inventing/blocking on an entity. Example still standing: `RefreshTokenEntity.widgetId` — `widget_id` FKs to `widget.widgets(id)` (added via `V63__auth_add_refresh_token_widget_fk.sql`, `ON DELETE SET NULL`) but no `WidgetEntity` exists yet. `owner_user_id` / `user_id` on the same kinds of tables *do* use a real `@ManyToOne` since `UserEntity` already exists.
  - **`ApiKeyEntity.tenant` was upgraded ahead of the normal rule**: `tenant_id` was mapped as a plain `BigInteger` until `TenantEntity` existed, and was then explicitly requested to be upgraded to `@ManyToOne TenantEntity tenant` in the same session `TenantPlanEntity` was implemented — even though `AGENTS.md` still notes api_keys have no functional usage until the tenant module is fully built. The FK relationship can be wired up before the feature that consumes it exists; don't assume "no usage yet" always means "leave as raw BigInteger" — check for an explicit instruction first.
- **`@Builder.Default` should mirror an actual DB `DEFAULT`, not invent business logic** — `AccountEntity.type` was given `@Builder.Default private String type = "oauth"` even though `auth.accounts.type` has no SQL default; this is a deliberate application-level choice made outside this convention, not a migration-mirroring default. Worth knowing this field can diverge from the "mirror the DB default" rule above.
- **`NOT NULL` without a DB default is still a plain required column, not a generated one** — e.g. `refresh_tokens.expires_at` is `TIMESTAMPTZ NOT NULL` with no `DEFAULT`, so `RefreshTokenEntity.expiresAt` is just `@Column(nullable = false)`, not `@CreationTimestamp`/`@UpdateTimestamp` or a `@Builder.Default`. The app is expected to always supply it explicitly.
- **A table may have `created_at` with no `updated_at`** — `auth.refresh_tokens` only has `created_at` (`@CreationTimestamp`, no `@UpdateTimestamp`); tokens are immutable once issued (revoked via `revoked_at`, not row updates). Don't assume the pair always comes together — check the migration.
- **Renamed columns**: `refresh_tokens.client` was renamed to `device_name` in `V76__rename_refresh_tokens_client.sql`. When a later migration renames/alters a column, map the entity to the *current* column name, not the one in the original `CREATE TABLE`.
- **Renamed tables**: `tenant.domains` was renamed to `tenant.tenant_domains` via `V73__rename_tenant_domain.sql` (the original `CREATE TABLE` is still `V25__tenant_domains.sql`). `@Table(schema, name)` must target the post-rename name — check for a later `ALTER TABLE ... RENAME TO` migration before trusting the `CREATE TABLE` file alone.
- **Skeleton files can have copy-paste bugs** — `RefreshTokenEntity`'s stub had `@Table(name = "api_keys")` (leftover from `ApiKeyEntity`). Verify `@Table(schema, name)` against the actual migration filename/table before trusting a pre-existing stub.
- **Multiple unresolved FKs on one table, resolved incrementally**: `TenantEntity` (`tenant.tenants`, `V24__tenant_tenants.sql`) FKs to four different tables. `owner_user_id` → `auth.users` was always a real `@ManyToOne UserEntity` since `UserEntity` already existed. `ecosystem_id` → `tenant.ecosystems`, `plan_id` → `tenant.plans`, and `organization_id` → `organization.organizations` all started as plain `BigInteger`, then were each upgraded — to `@ManyToOne EcosystemEntity ecosystem`, `@ManyToOne TenantPlanEntity plan`, and `@ManyToOne OrganizationEntity organization` respectively — once their target entity got implemented. When a sibling entity for an existing raw-FK field is implemented, go back and upgrade that field to the real relationship rather than leaving it as a `BigInteger`. Apply the "does the target entity exist yet" test per-column, not per-table.
- **`default_locale public.locale NOT NULL DEFAULT 'en'`** (`TenantEntity.defaultLocale`) reuses the shared `global/enums/Locale` enum (same pattern as `UserEntity.locale`) since it's a `public`-schema enum, not a `tenant`-schema one — `@Builder.Default = Locale.en` mirrors the SQL default.
- **`EcosystemEntity`** (`tenant.ecosystems`, `V23__tenant_ecosystems.sql`) is a simple lookup table with no FKs: `code`/`name`/`icon` are plain required `String` columns, `description` is `TEXT NOT NULL` (no `length` set), `status` uses the `tenant`-scoped `EcosystemStatus` enum with `@Builder.Default = EcosystemStatus.REVIEWING` mirroring the SQL `DEFAULT 'REVIEWING'`, and `metadata` is nullable `JsonNode`.
- **`TenantPlanEntity`** (`tenant.plans`, `V22__tenant_plans.sql`) is another FK-free lookup table: `code`/`name` are plain `String`, `price` is `BigDecimal` via `@Column(precision = 10, scale = 2)` matching `NUMERIC(10, 2)`, `currency` reuses the shared `global/enums/Currency` (a `public`-schema enum) with `@Builder.Default = Currency.USD` mirroring the SQL `DEFAULT 'USD'`, the four `max_*` columns are plain `Integer`, and both `features`/`metadata` are nullable `JsonNode`. Its PK is `tenantPlanId` (see the class-name-driven PK rule above), not `planId`.
- **`TenantDomainEntity`** (`tenant.tenant_domains`, originally `V25__tenant_domains.sql`, table renamed by `V73__rename_tenant_domain.sql`): single FK `tenant_id` → `@ManyToOne TenantEntity tenant` since `TenantEntity` already exists. `verified BOOLEAN NOT NULL DEFAULT false` and `is_primary BOOLEAN NOT NULL DEFAULT true` map to `Boolean` fields with `@Builder.Default` mirroring their literal SQL defaults (`isPrimary` for `is_primary`, following the same camelCase-column convention as every other field). `verification_token` is a plain required `String` (`TEXT` column, no `length`).
- **`OrganizationEntity`** (`organization.organizations`, `V18__organization_organizations.sql`) is a root FK-free entity — every other `organization` table (`profiles`, `memberships`) and cross-schema table (`tenant.tenants`, `core.services`, `notification.notifications`, `resource.resource_types`/`resources`, `audit.audit_events`, `customer.customers`) FKs into it, but it FKs to nothing itself. PK is `organizationId`. `name`/`slug` are plain required `String` (`slug` also `unique = true`); `logoUrl`/`bannerUrl`/`bio` are nullable `TEXT` columns with no `length`. `isPrivate BOOLEAN NOT NULL DEFAULT false` and `timezone VARCHAR(100) NOT NULL DEFAULT 'Australia/Sydney'` are `@Builder.Default` mirroring their SQL defaults. `weekStart` reuses the shared `global/enums/WeekStart` (a `public`-schema enum, values `SUNDAY`/`MONDAY`) with `@Builder.Default = WeekStart.MONDAY` mirroring `DEFAULT 'MONDAY'`. `metadata` is nullable `JsonNode`.
- **`MembershipEntity`** (`organization.memberships`, `V20__organization_memberships.sql`) has both its FKs resolved from the start since `OrganizationEntity` and `UserEntity` already existed: `organization_id` → `@ManyToOne OrganizationEntity organization`, `user_id` → `@ManyToOne UserEntity user`. PK is `membershipId`. `accepted BOOLEAN NOT NULL DEFAULT false` is `@Builder.Default`. No `metadata`/JSON columns on this table. `organization.membership_roles` (`V21__organization_membership_roles.sql`) FKs into this table's `id` — once `MembershipRoleEntity` is implemented it should get a real `@ManyToOne MembershipEntity membership`.
- **`ProfileEntity`** (`organization.profiles`, `V19__organization_profiles.sql`) — per-organization user profile (distinct from `MembershipEntity`, which just tracks org membership/acceptance). Both FKs resolved from the start: `user_id` → `@ManyToOne UserEntity user`, `organization_id` → `@ManyToOne OrganizationEntity organization`. PK is `profileId`; `uid UUID NOT NULL DEFAULT gen_random_uuid()` follows the standard `@UuidGenerator` pattern as `profileUid`. `username VARCHAR(100) NOT NULL` is a plain required `String` with `length = 100` (uniqueness is per-organization via `uq_profiles_username_organization`, not enforced at the entity level). No `metadata`/JSON columns on this table.
- **`MembershipRoleEntity`** (`organization.membership_roles`, `V21__organization_membership_roles.sql`) is the first pure join table with a composite PK: `PRIMARY KEY (membership_id, role_id)`, no surrogate `id`. Modeled with `@EmbeddedId` + a `MembershipRoleId` class (`organization/membershiprole/id/MembershipRoleId.java` — composite-key ID classes get their own `id/` package alongside `entity/`), and `@MapsId("membershipId")` / `@MapsId("roleId")` on the two `@ManyToOne` associations (`membership` → `MembershipEntity`, `role` → `RoleEntity`) so the FK columns double as the PK. The `@EmbeddedId` field itself needs `@Builder.Default = new MembershipRoleId()` (not left null) — `@MapsId` populates the embeddable's sub-fields by reflection off the associated entities at flush time, which requires a non-null instance to write into. `created_at` was renamed to `assigned_at` by `V75__rename_membership_roles_created_at.sql`; since the table has only that one timestamp with `DEFAULT now()` and no update counterpart (same shape as `auth.refresh_tokens`), it maps to `@CreationTimestamp` + `updatable = false`, not a `@Builder.Default` literal — `Instant.now()` as a Lombok builder default gets re-evaluated at object-build time (and per Lombok's generated supplier, on every `build()` call that doesn't set it explicitly) rather than at actual persist time, which drifts from the DB-consistent `@CreationTimestamp` pattern used everywhere else. A hand-rolled `@Embeddable` id class also needs real `equals()`/`hashCode()` (composite/`@MapsId` keys require it for Hibernate's identity checks) — write the full field comparison, not just the reference/null/class-mismatch guard clauses; a guard-only `equals()` won't even compile (missing return on the remaining path).
- **`WidgetEntity`** (`widget.widgets`, `V47__widgets.sql`, indexes in `V69__indexes_widget.sql`): `tenant_id` → `@ManyToOne TenantEntity tenant` since `TenantEntity` already exists; `service_id` → `@ManyToOne ServiceEntity service` (`nullable = false`) — originally a plain `BigInteger serviceId` back when the entire `core/` package was still empty, upgraded to a real relationship on explicit instruction once `ServiceEntity` existed, same precedent as `ApiKeyEntity.tenant`. `status` uses the `widget`-scoped `WidgetStatus` enum with `@Builder.Default = WidgetStatus.REGISTERING`, `type` uses `WidgetType` with `@Builder.Default = WidgetType.EMBEDDED`, both mirroring their SQL `DEFAULT`s. `origin_validation BOOLEAN NOT NULL DEFAULT false` is `@Builder.Default`. `public_key`/`secret_key` are plain required `String` (`public_key` also `unique = true`, matching `uq_widgets_public_key`). This table has **three** `TIMESTAMPTZ DEFAULT now()` columns, not the usual pair: `issued_at`, plus the standard `created_at`/`updated_at` at the end (per column-ordering convention). `issued_at` is mapped `@CreationTimestamp` (no `updatable = false`) rather than a `@Builder.Default = Instant.now()` literal, consistent with the project's standing preference (see `MembershipRoleEntity.assignedAt` note above) for `@CreationTimestamp` over Lombok-builder-time `Instant.now()` on any `DEFAULT now()` timestamp column — even a business-semantic one like "issued at" rather than a pure audit column. `updatable = false` was deliberately omitted here (unlike `createdAt`) since `issued_at` is plausibly refreshed on key rotation, not strictly immutable like `created_at`. `last_used_at` is a nullable `Instant` with no default. `uid UUID NOT NULL DEFAULT gen_random_uuid()` follows the standard `@UuidGenerator` pattern as `widgetUid`.
- **`WidgetOriginEntity`** (`widget.widget_origins`, `V48__widget_origins.sql`): `widget_id` → `@ManyToOne WidgetEntity widget` (`nullable = false`); `created_by` → `@ManyToOne UserEntity user` but **nullable**, matching `created_by BIGINT` (no `NOT NULL`) and `ON DELETE SET NULL`. `origin` is a plain required `String`. `verified BOOLEAN NOT NULL DEFAULT false` is `@Builder.Default`. Only `created_at` exists (`@CreationTimestamp`, `updatable = false`) — no `updated_at` column in the migration, same shape as `auth.refresh_tokens`.
- **`ScheduleEntity`** (`core.schedules`, `V26__core_schedules.sql`, index in `V67__indexes_core.sql`): first entity implemented in the `core` bounded context. `user_id` → `@ManyToOne UserEntity user` since `UserEntity` already exists. `title` is a plain required `String`. `timezone VARCHAR(100) NOT NULL DEFAULT 'Australia/Sydney'` is `@Builder.Default` mirroring the SQL default (same default value as `OrganizationEntity.timezone`). Only `created_at`/`updated_at` — no `uid` column on this table. PK is `scheduleId`.
- **`AvailabilityEntity`** (`core.availabilities`, `V27__core_availabilities.sql`, indexes in `V67__indexes_core.sql`): both FKs resolved from the start — `user_id` → `@ManyToOne UserEntity user`, `schedule_id` → `@ManyToOne ScheduleEntity schedule` (now that `ScheduleEntity` exists). `days INTEGER[] NOT NULL` is the first native array column in the codebase — mapped `Integer[] days` via `@JdbcTypeCode(SqlTypes.ARRAY)` (see array-column convention above). `start_time`/`end_time` are `TIME NOT NULL` columns mapped to plain required `java.time.LocalTime` (no default). Only `created_at`/`updated_at` — no `uid` column. PK is `availabilityId`.
- **`ServiceEntity`** (`core.services`, `V28__core_services.sql`, indexes in `V67__indexes_core.sql`, plus two later `ALTER TABLE` migrations): the most FK-heavy `core` table so far. Four FKs, all resolved to real `@ManyToOne` since every target entity already exists: `user_id` → `UserEntity`, `profile_id` → `ProfileEntity`, `organization_id` → `OrganizationEntity`, `schedule_id` → `ScheduleEntity`. `interface_language public.locale NOT NULL DEFAULT 'en'` and `currency public.currency NOT NULL DEFAULT 'USD'` reuse the shared `global/enums` (`Locale`, `Currency`) with `@Builder.Default` mirroring their SQL defaults — same pattern as `TenantEntity`/`TenantPlanEntity`. `period_type VARCHAR(50) NOT NULL DEFAULT 'UNLIMITED'` is a plain `String` with `@Builder.Default`, **not** a native enum — it's a `VARCHAR` column in the migration, not `public.<type>`, even though `core/enums/BookingMode` exists; don't conflate a look-alike scaffolded enum with an actual native-enum column, only the migration's declared column type decides. `min_price`/`max_price NUMERIC(10, 2)` are nullable `BigDecimal` (`precision = 10, scale = 2`, no default, matching `TenantPlanEntity.price`'s type pattern). `requires_confirmation`/`disable_cancelling`/`disable_rescheduling`/`is_instant_service` are all `BOOLEAN NOT NULL DEFAULT false` → `Boolean` with `@Builder.Default = false`. `description`/`location`/`success_redirect_url` are nullable `TEXT`/`String`, `max_active_booking_per_booker` nullable `Integer`, `metadata` nullable `JsonNode`. `destination_calendar_id` (added by `V51__core_add_destination_calendar_fk.sql`) and `destination_sheets_id` (added by `V77__core_add_destination_sheets_fk.sql`) both FK into `integration` schema tables (`ON DELETE SET NULL`, no `NOT NULL`) — originally stayed plain nullable `BigInteger` while no `integration` entity existed, upgraded to real `@ManyToOne DestinationCalendarEntity destinationCalendar` / `@ManyToOne DestinationSheetsEntity destinationSheets` on explicit instruction once `DestinationCalendarEntity`/`DestinationSheetsEntity` were implemented — and per the `createdAt`/`updatedAt`-always-last convention, both are placed **before** `created_at`/`updated_at` in the entity even though Postgres physically appended them after those columns when the `ALTER TABLE`s ran. PK is `serviceId`. Uniqueness (`uq_services_organization_slug` on `(organization_id, slug)`) is DB-level only, same as `ProfileEntity.username` — not enforced at the entity level.
- **`BookingEntity`** (`core.bookings`, `V30__core_bookings.sql`, indexes in `V67__indexes_core.sql`, plus `V51__core_add_destination_calendar_fk.sql` and `V78__rename_booking_cancelation_reason.sql`): the busiest FK table in `core` so far — four separate FKs into `auth.users` alone (`user_id`, `cancelled_by`, `rescheduled_by`, `deleted_by`), all mapped as real `@ManyToOne UserEntity` with distinct field names (`user`, `cancelledBy`, `rescheduledBy`, `deletedBy`) since `UserEntity` already exists; the latter three are nullable (`ON DELETE SET NULL`, no `NOT NULL`) matching the CODING_CONVENTIONS `core.bookings` `uid`-as-external-identifier note: `uid UUID NOT NULL DEFAULT gen_random_uuid()` (`unique = true`) is `@UuidGenerator` as `bookingUid`, same pattern as every other `uid` column. `service_id` → `@ManyToOne ServiceEntity service`. `status core.booking_status NOT NULL DEFAULT 'PENDING'` reuses `core/enums/BookingStatus` (native enum, values match `V3__create_enum_types.sql` exactly) with `@Builder.Default = BookingStatus.PENDING`. `paid`/`rescheduled`/`no_show_host` are `BOOLEAN NOT NULL DEFAULT false` → `Boolean` `@Builder.Default = false`. `idempotency_key`/`description`/`location`/`rejection_reason` are nullable `String`; `deleted_at` is a nullable `Instant` with no default (soft-delete marker, plain column, not `@CreationTimestamp`/`@UpdateTimestamp`). `metadata` nullable `JsonNode`. Same as `ServiceEntity`: `destination_calendar_id`/`destination_sheets_id` (both added by `V51__core_add_destination_calendar_fk.sql`, which — despite its filename — adds both columns to `core.bookings` in one migration) originally stayed plain nullable `BigInteger` (no `integration` entity yet, flagged with a `// Missing destination calendar & sheets` comment above the class), then were upgraded to real `@ManyToOne DestinationCalendarEntity destinationCalendar` / `@ManyToOne DestinationSheetsEntity destinationSheets` on explicit instruction once `DestinationCalendarEntity`/`DestinationSheetsEntity` were implemented — flag comment removed accordingly — and placed before `created_at`/`updated_at` per the always-last convention. PK is `bookingId`. **Rename missed on first pass, corrected afterward**: `cancelation_reason` (as originally spelled in `V30`) was renamed to `cancellation_reason` by `V78__rename_booking_cancelation_reason.sql` — the entity field is `cancellationReason`/`@Column(name = "cancellation_reason")`. The rename migration was present in the repo the whole time and a `grep -rli "core\.bookings\b"` over the migration folder does match it, but it was overlooked on the initial implementation pass and only caught on a later correction — a reminder to re-run the full-table grep (not just skim the first pass's results) before considering a table's migration history closed.
- **`BookingPolicyEntity`** (`core.booking_policies`, `V29__core_booking_policies.sql`): single FK, `service_id` → `@ManyToOne ServiceEntity service`. `booking_mode core.booking_mode NOT NULL DEFAULT 'FIXED'` reuses `core/enums/BookingMode` (native enum) with `@Builder.Default = BookingMode.FIXED`. `duration_type`/`booking_window_type` are both `VARCHAR(50) NOT NULL` with **no** SQL default — plain required `String`, same "required but no `@Builder.Default`" treatment as `RefreshTokenEntity.expiresAt`; don't confuse these with `ServiceEntity.periodType`, which *does* have a SQL default and so does get `@Builder.Default`. `minimum_notice`/`maximum_advance_booking`/`capacity` are `INTEGER NOT NULL` with no default → plain required `Integer`. `default_duration`/`slot_interval`/`before_buffer`/`after_buffer` all have `INTEGER ... - **`AuditResourceEntity`** (`audit.audit_resources`, `V60__audit_resources.sql`, index in `V72__indexes_audit.sql`): single FK in the migration, `event_id BIGINT NOT NULL` → `audit.audit_events(id)` `ON DELETE CASCADE` — originally left as a plain `BigInteger eventId` while `AuditEventEntity` was still an empty skeleton, then upgraded to `@ManyToOne AuditEventEntity event` (`nullable = false`) once `AuditEventEntity` was implemented, same precedent as `ApiKeyEntity.tenant`/`WidgetEntity.service`. `resource_type audit.resource_type NOT NULL` reuses `audit/enums/ResourceType` (native enum, values confirmed against `V3__create_enum_types.sql`) as `@Enumerated(STRING)` + `@JdbcTypeCode(NAMED_ENUM)`, no `@Builder.Default` (required-but-no-default). `resource_uid`/`resource_name VARCHAR(255) NOT NULL` are required `String`. `before_snapshot JSONB` nullable `JsonNode`; `after_snapshot JSONB NOT NULL` required `JsonNode` — first table with one nullable and one required JSONB column side by side. Only `created_at` — no `updated_at`. PK is `auditResourceId`.
- **`AuditEventEntity`** (`audit.audit_events`, `V59__audit_events.sql`, indexes in `V72__indexes_audit.sql`) is the central `audit`-schema table — three FKs, all resolved to real `@ManyToOne` since every target entity already exists: `tenant_id` → `TenantEntity` (nullable, `ON DELETE SET NULL`), `organization_id` → `OrganizationEntity` (nullable, `ON DELETE SET NULL`), `actor_id` → `AuditActorEntity` (`nullable = false`, `ON DELETE CASCADE` — unlike the deliberately FK-less columns on `AuditActorEntity` itself, `audit_events.actor_id` **is** a real DB FK, so it gets a real relationship). `uid UUID NOT NULL DEFAULT gen_random_uuid()` (`unique = true`, matching `uq_audit_events_uid`) → `@UuidGenerator auditEventUid`, standard pattern. `correlation_id`/`request_id`/`trace_id VARCHAR(255)` are all nullable `String`. `event_domain audit.event_domain NOT NULL` reuses `audit/enums/AuditDomain` (native enum — Java class is named `AuditDomain`, not `EventDomain`, despite the column/Postgres-type being `event_domain`; values confirmed against `V3__create_enum_types.sql`). `event_type`/`action`/`severity`/`status` reuse `EventType`/`AuditAction`/`Severity`/`AuditStatus` respectively (all native enums, all `@Enumerated(STRING)` + `@JdbcTypeCode(NAMED_ENUM)`, none with `@Builder.Default` — required-but-no-default across the board). `context JSONB` is nullable `JsonNode`. `event_version INTEGER NOT NULL DEFAULT 1` → `@Builder.Default = 1`. # Entity relationships

- **Many-to-one (owning FK side)**: `@ManyToOne(fetch = FetchType.LAZY)` + `@JoinColumn(name = "<fk_column>", nullable = ...)`, matching the migration's `NOT NULL`/nullability on the FK column. Examples: `AccountEntity.user` → `auth.accounts.user_id`; `ApiKeyEntity.tenant` → `auth.api_keys.tenant_id` (cross-bounded-context FK, `auth` entity pointing at `tenant`). DB-level `ON DELETE CASCADE` is not mirrored as a JPA cascade — cascade behavior lives in the DB, not the entity.
- **Many-to-many**: `@Builder.Default Set<...> = new HashSet<>()` + `@ManyToMany(fetch = FetchType.EAGER)` + `@JoinTable(joinColumns = ..., inverseJoinColumns = ...)`. Examples: `UserEntity.roles` (via `auth.user_roles`), `RoleEntity.permissions` (via `auth.role_permissions`).
  - **Inconsistency to watch**: `UserEntity`'s `@JoinTable` sets `schema = "auth"` explicitly; `RoleEntity`'s does not (relies on the default schema even though `role_permissions` lives in `auth`). Reconcile if it causes a resolution issue.

# Service & Controller conventions

Established with `UserController`/`UserService`/`UserServiceImpl` — the first controller, service, and DTO pair implemented in the codebase, so this is the reference pattern for every subdomain's CRUD layer going forward. `/Users/trungnguyen/Documents/Code/SoftwareEngineering/BusinessProjects/pleasebookme/CODING_CONVENTIONS.md` (repo root, one level up from `server/`) is the authoritative source for these rules — check it before adding a new controller/service/DTO, it isn't `@`-included from `CLAUDE.md`/`SERVER_AGENTS.md` so it's easy to miss.

- **Controller**: `@RestController` + `@RequestMapping("/api/v1/<plural-resource>")`, constructor injection via Lombok `@RequiredArgsConstructor` (not field `@Autowired`). Standard REST verbs: `POST` (create, `@ResponseStatus(HttpStatus.CREATED)`), `GET /{id}` (read one), `GET` (read all), `PUT /{id}` (update, full-replace semantics — the caller is expected to send the complete resource, not a partial patch), `DELETE /{id}` (`@ResponseStatus(HttpStatus.NO_CONTENT)`, no body). Controllers only translate between DTOs and the service layer — no entity references, no business logic.
  - **Known deviation from `CODING_CONVENTIONS.md`**: that file says controllers should "always return `ResponseEntity` with status number if possible," but `UserController` currently returns bare DTOs plus a class-level `@ResponseStatus` annotation instead. Not yet reconciled — only flagged here so the next controller (or a follow-up pass on `UserController`) picks the `ResponseEntity<T>` form when asked.
- **DTOs**: `CODING_CONVENTIONS.md` mandates records for every DTO. `dto/UserRequest` and `dto/UserResponse` are both plain `record`s (no Lombok on either — records get their own canonical constructor/accessors for free, so `@Getter`/`@Builder`/`@AllArgsConstructor` would be redundant). Record accessors follow record naming (`request.username()`, not `request.getUsername()`) — callers in the service layer use the bare accessor form. `UserResponse` keeps a static `from(UserEntity)` factory method (records can carry static methods same as any class) that maps entity → DTO field-by-field via the canonical constructor. Request/response DTOs only carry the subset of entity fields that make sense as external input/output — relationship collections (e.g. `UserEntity.roles`) and free-form `metadata` are deliberately left off both DTOs for now, not because they're unsupported, but because CRUD for those isn't in scope yet; add fields when a concrete need shows up rather than exposing everything preemptively.
- **Service interface + impl**: interface in `service/`, implementation in `service/impl/` as `<Name>ServiceImpl`, `@Service` + `@RequiredArgsConstructor` injecting the repository. Standard CRUD method set: `create<Entity>(RequestDto)`, `get<Entity>ById(id)` (plus any existing custom finders like `getUserByEmail`/`getUserByPhone`), `getAll<Entity>s()`, `update<Entity>(id, RequestDto)`, `delete<Entity>(id)`. `create`/`update` build/mutate the entity via its Lombok builder/setters directly from the request record's accessors — no separate mapper class.
- **Not-found/conflict handling**: superseded the original `ResponseStatusException`-only approach — a `@ControllerAdvice` now exists at `global/handler/GlobalExceptionHandler.java`, mapping typed exceptions to a shared `global/response/ApiErrorResponse.java` shape (`status`/`message`/`data`/`client`/`timestamp`/`path`). Per-subdomain exceptions live in that subdomain's own `exception/` package (e.g. `auth/user/exception/UserNotFoundException.java` + `DuplicateUserException.java`, `auth/password/exception/UserPasswordNotFoundException.java` + `DuplicateUserPasswordException.java`) — plain `RuntimeException` subclasses with a single `String message` constructor, no shared base class. Each gets its own `@ExceptionHandler` method in `GlobalExceptionHandler`: `*NotFoundException` → `HttpStatus.NOT_FOUND`, `Duplicate*Exception` → `HttpStatus.CONFLICT`. `global/exception/ResourceNotFoundException.java` still exists as a generic fallback for subdomains without their own typed exception yet. New subdomains should follow this typed-exception-per-domain pattern rather than throwing `ResponseStatusException` directly from the service layer.
- **Duplicate-check-before-create**: `create<Entity>` methods check uniqueness via repository `existsBy*`/`existsById` calls *before* building the entity, throwing the domain's `Duplicate*Exception` on a hit — established on `UserServiceImpl.createUser` (`existsByUsername`/`existsByEmail`/`existsByPhone`) and carried into `UserPasswordServiceImpl.createUserPassword` (`existsById`, since `UserPasswordEntity`'s PK **is** the FK). This matters most for shared-PK/`@MapsId` entities: `JpaRepository.save()` on an entity with a non-null `@Id` does a `merge` (silent UPDATE), not an INSERT-or-fail, so without the `existsById` guard a "create" call would silently overwrite an existing row instead of erroring.
- **CRUD for a shared-PK (`@MapsId`) entity**: `UserPasswordServiceImpl` is the first CRUD service built over a derived-identity entity (see `UserPasswordEntity`'s shared-PK note above). To create one, fetch the *parent* entity via its own repository (`UserRepository.findById(request.userId())`, throwing the parent's own `UserNotFoundException` if missing) and set only the association (`.user(user)`) on the builder — **not** the raw `@Id` field (`userId`) directly; Hibernate derives it from the association via `@MapsId` at flush time. `update`/`delete` key off `userId` exactly like `User`'s CRUD keys off its own PK, since here the shared PK doubles as the natural identifier.
  - **No "get all" endpoint**: unlike `User`, `UserPasswordController`/`UserPasswordService`/`UserPasswordServiceImpl` deliberately have **no** `getUserPasswords()`/`getAllUserPasswords()` — a bulk-list endpoint over a credentials table (even with `raw` since dropped from `PasswordResponse`) was removed on request rather than kept for CRUD-completeness symmetry with `User`. Don't re-add it by default when extending this controller; treat per-user lookup (`GET /{userId}`) as the only supported read shape here.
  - **`PasswordResponse` excludes `raw`**: unlike the original implementation (which mirrored every entity column, `UserResponse`-style), `PasswordResponse` was edited to drop the plaintext `raw` field from the API response — it still exists on `PasswordRequest`/`UserPasswordEntity` for the [[db_raw_password_field]]-documented onboarding-phase storage reason, but the response DTO no longer echoes it back over the wire.
  - **Password-reuse check on update**: `updateUserPassword` rejects a request whose `raw` equals the currently stored `raw`, throwing `DuplicateUserPasswordException` (→ 409, same handler as the create-time duplicate check). The comparison is a plain `String.equals` on plaintext — consistent with [[db_raw_password_field]]'s standing decision that `raw` is intentionally stored unhashed during the private-onboarding phase, not something to route through a hashing/verification layer that doesn't exist yet.
- **Bean validation**: `spring-boot-starter-validation` was added to `build.gradle.kts` once `UserRequest` needed constraint annotations, so `jakarta.validation.constraints.*` and `@Valid` are now available/wired up project-wide. `UserRequest` maps its `jakarta.validation` annotations directly off `V10__auth_users.sql`'s column definitions — `@NotBlank` on every `NOT NULL`-with-no-SQL-default `String` column (`username`, `name`, `email`, `phone`), `@Size(max = n)` mirroring each `VARCHAR(n)` length (`username` 100, `name`/`email` 255, `phone` 50, `timezone` 100), and no annotation on `bio`/`avatarUrl` (`TEXT`, nullable, no length limit). Columns with a SQL `DEFAULT` (`locale`, `timezone`, `theme`, `weekStart`) stay unannotated for nullability (no `@NotNull`) since the service layer already treats a null request value as "use the DB/entity default" (see `UserServiceImpl`'s `if (request.x() != null)` guards) — only `timezone`'s `@Size` applies when a value is actually supplied. Deliberately no `@Email` on `email` — the migration only declares `VARCHAR(255) NOT NULL`, no format constraint, and the ask was to mirror the migration exactly, not add extra validation semantics. For validation to actually trigger, `UserController`'s `createUser`/`updateUser` `@RequestBody UserRequest` parameters both need `@Valid` — added alongside the DTO annotations, otherwise the constraints are inert. A failed `@Valid` currently surfaces as Spring's default `MethodArgumentNotValidException` 400 response (no custom `@ExceptionHandler` shaping it yet, consistent with the "no global `@ControllerAdvice`" note above).
- **CRUD for pure composite-PK join tables (no surrogate `id`, no `@MapsId`)**: `UserRoleServiceImpl`/`RolePermissionServiceImpl` are the first CRUD services built directly over `UserRoleEntity`/`RolePermissionEntity` (both `@EmbeddedId`-keyed join tables, see their entity notes above). Repository is `JpaRepository<Entity, EmbeddedIdClass>` (e.g. `JpaRepository<UserRoleEntity, UserRoleId>`), so `findById`/`existsById`/`delete` all take a constructed `new UserRoleId(userId, roleId)` rather than a single scalar — no custom finder methods needed. `create` resolves *both* sides via their own repositories (`UserRepository`/`RoleRepository`, throwing each side's own `*NotFoundException`) and builds via `.user(user).role(role)` — same "set the association, not the raw FK field" pattern as the `UserPassword` `@MapsId` precedent — plus an `existsById` duplicate-check before create (`DuplicateUserRoleException`/`DuplicateRolePermissionException`, → 409). Controllers expose the composite key as two path segments: `GET/DELETE /api/v1/user-roles/{userId}/{roleId}`. **Deliberately no `update` endpoint/service method on either domain** — a join table with nothing but the composite key (`RolePermissionEntity`) or the key plus an immutable `@CreationTimestamp` (`UserRoleEntity.assignedAt`) has no mutable, non-key attribute to update; the only meaningful mutations are create (assign) and delete (revoke). Don't add a no-op `update` here by default — this mirrors the `UserPassword` precedent of omitting a CRUD verb that doesn't semantically fit the entity's actual shape (there: no bulk-list; here: no update).
