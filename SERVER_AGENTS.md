# Infrastructure

- `infrastructure/docker/compose.yml` runs `postgres:16`, `redis:7.4-alpine`, and `pgadmin4`. Spring Boot's docker-compose integration starts/stops it automatically (`spring.docker.compose.enabled: true`, `lifecycle-management: start-and-stop`, file path `../infrastructure/docker/compose.yml`).
- **Two separate `.env` files, both gitignored**: `infrastructure/docker/.env` is read by docker compose (interpolates `${REDIS_PASSWORD}` etc. into `compose.yml`); `server/.env` is read by `build.gradle.kts` and injected into `bootRun`/`test` as environment variables. Keys shared by both (e.g. `REDIS_PASSWORD`) **must be kept in sync by hand** — a mismatch surfaces as `WRONGPASS` at runtime, not at startup.
- Redis is password-protected via `--requirepass`, bound to `127.0.0.1` only, `--appendonly yes`, and `--maxmemory-policy noeviction`. The eviction policy is deliberate: the default `allkeys-lru` would silently evict OAuth state entries under memory pressure, turning a valid consent callback into "invalid state" for a real user. Failing writes loudly beats silently dropping security state.
- The redis service carries the label `org.springframework.boot.ignore: "true"`. Without it, `spring-boot-docker-compose` auto-detects the container and injects `RedisConnectionDetails` that **override** `application.yaml` — and since the plain `redis` image exposes no password environment variable, that auto-detected connection has no password and fails. The label keeps `application.yaml` as the single source of truth and makes local behave like production.

# CORS

- Configured in `security/config/WebConfig.java` from `CorsProperties` (`app.cors.*`, validated at startup).
- **Two registrations are required, not one.** `WebMvcConfigurer.addCorsMappings` alone is not enough: Spring Security's filter chain runs *before* the DispatcherServlet, so a preflight never reaches the MVC layer. `WebConfig` therefore also exposes a `CorsConfigurationSource` bean, and `SecurityConfig` calls `.cors(Customizer.withDefaults())` to consult it. Omitting that one line in `SecurityConfig` makes the entire CORS configuration inert.
- Verified behaviour: an allowed origin gets a 200 preflight with full `Access-Control-*` headers; a disallowed origin gets 403 with no `Access-Control-Allow-Origin`.

# Migrations

- Authored with comments in `database/init/<domain>/`, then mirrored comment-free into `server/src/main/resources/db/migration/<domain>/` on request.
- SQL conventions: `BIGSERIAL` PKs, named FK/index constraints, single-line FK/index formatting, zero comments in the Flyway copy.
- **Current applied schema version: v141.**
- **Renumbering a migration below the applied high-water mark breaks the boot.** A previous session renumbered `V112 → V119` while `120/121/122` were already applied, which left a *pending* migration below the current version. Flyway's `validate` rejects that with `Detected resolved migration not applied to database: 119` and the application refuses to start — the failure surfaces as an opaque `entityManagerFactory` bean-creation error, several `Caused by` levels above the real cause. Fixed by renumbering to `V125` (above the mark). Before renumbering anything, check `SELECT MAX(version::numeric) FROM flyway_schema_history WHERE success` and keep pending migrations strictly above it. Since the migration had never been applied, no `flyway_schema_history` rewrite was needed; had it been applied, the ledger would have had to be edited by hand too.

# Package structure

Domain-driven, one folder per subdomain under its bounded context, each with `entity/`, `repository/`, `service/`, `controller/`, `dto/` (created as needed, not all populated upfront):

```text
auth/
  user/, role/, permission/, account/, apikey/, attribute/,
  password/, refreshtoken/, rolepermission/, session/, userrole/
  handoff/store/  <- SessionHandoffStore + RedisSessionHandoffStore. No entity,
                     no repository, no table - Redis-backed, mirroring
                     integration/oauthstate/. Don't add a migration.
  enums/          <- auth-schema-specific enums (e.g. AccountStatus)
global/
  enums/          <- cross-schema/public-schema enums (Locale, Theme, WeekStart, Currency)
  exception/, handler/, response/, utils/
security/
  authorization/, config/, identity/, oauth/, permission/, policy/, token/
  crypto/           <- TokenCipher/AesGcmTokenCipher + config/, exception/
  identity/context/ <- CurrentPrincipalProvider (read the principal back out)
  oauth/google/     <- config/, identity/, verifier/, authorization/, client/, exception/
service/
  auth/             <- AuthService, GoogleSignInService, UserProvisioningService,
                       GoogleAccountResolver, SessionIssuer, GoogleOnboardingService
  integration/      <- GoogleConnectService, GoogleAccessTokenProvider, controller/
```

`service/` is the orchestration layer, distinct from the bounded contexts. `service/auth/` and `service/integration/` hold cross-domain business flows (login, register, Google sign-in, Google consent) that coordinate several repositories and the `security/` infrastructure; the bounded-context packages hold per-table CRUD. When adding a flow that spans domains, it belongs under `service/<area>/`, not inside one domain's `service/`.

Other top-level bounded contexts mirror the schemas: `analytics`, `audit`, `billing`, `core`, `customer`, `feature` (appointment/auth/notification/slot/workspace), `integration`, `notification`, `organization`, `resource`, `tenant`, `webhook`, `widget`.

# Service & Controller conventions

Established with `UserController`/`UserService`/`UserServiceImpl` — the first controller, service, and DTO pair implemented in the codebase, so this is the reference pattern for every subdomain's CRUD layer going forward. `/Users/trungnguyen/Documents/Code/SoftwareEngineering/BusinessProjects/pleasebookme/CODING_CONVENTIONS.md` (repo root, one level up from `server/`) is the authoritative source for these rules — check it before adding a new controller/service/DTO, it isn't `@`-included from `CLAUDE.md`/`SERVER_AGENTS.md` so it's easy to miss.

- **Controller**: `@RestController` + `@RequestMapping("/api/v1/<plural-resource>")`, constructor injection via Lombok `@RequiredArgsConstructor` (not field `@Autowired`). Standard REST verbs: `POST` (create, `@ResponseStatus(HttpStatus.CREATED)`), `GET /{id}` (read one), `GET` (read all), `PUT /{id}` (update, full-replace semantics — the caller is expected to send the complete resource, not a partial patch), `DELETE /{id}` (`@ResponseStatus(HttpStatus.NO_CONTENT)`, no body). Controllers only translate between DTOs and the service layer — no entity references, no business logic.
  - **Known deviation from `CODING_CONVENTIONS.md`**: that file says controllers should "always return `ResponseEntity` with status number if possible," but `UserController` currently returns bare DTOs plus a class-level `@ResponseStatus` annotation instead. Not yet reconciled — only flagged here so the next controller (or a follow-up pass on `UserController`) picks the `ResponseEntity<T>` form when asked.
- **DTOs**: `CODING_CONVENTIONS.md` mandates records for every DTO. `dto/UserRequest` and `dto/UserResponse` are both plain `record`s (no Lombok on either — records get their own canonical constructor/accessors for free, so `@Getter`/`@Builder`/`@AllArgsConstructor` would be redundant). Record accessors follow record naming (`request.username()`, not `request.getUsername()`) — callers in the service layer use the bare accessor form. `UserResponse` keeps a static `from(UserEntity)` factory method (records can carry static methods same as any class) that maps entity → DTO field-by-field via the canonical constructor. Request/response DTOs only carry the subset of entity fields that make sense as external input/output — relationship collections (e.g. `UserEntity.roles`) and free-form `metadata` are deliberately left off both DTOs for now, not because they're unsupported, but because CRUD for those isn't in scope yet; add fields when a concrete need shows up rather than exposing everything preemptively.
- **Service interface + impl**: interface in `service/`, implementation in `service/impl/` as `<Name>ServiceImpl`, `@Service` + `@RequiredArgsConstructor` injecting the repository. Standard CRUD method set: `create<Entity>(RequestDto)`, `get<Entity>ById(id)` (plus any existing custom finders like `getUserByEmail`/`getUserByPhone`), `getAll<Entity>s()`, `update<Entity>(id, RequestDto)`, `delete<Entity>(id)`. `create`/`update` build/mutate the entity via its Lombok builder/setters directly from the request record's accessors — no separate mapper class.
- **Not-found/conflict handling**: superseded the original `ResponseStatusException`-only approach — a `@ControllerAdvice` now exists at `global/handler/GlobalExceptionHandler.java`, mapping typed exceptions to a shared `global/response/ApiErrorResponse.java` shape (`status`/`message`/`data`/`client`/`timestamp`/`path`). Per-subdomain exceptions live in that subdomain's own `exception/` package (e.g. `auth/user/exception/UserNotFoundException.java` + `DuplicateUserException.java`, `auth/password/exception/UserPasswordNotFoundException.java` + `DuplicateUserPasswordException.java`) — plain `RuntimeException` subclasses with a single `String message` constructor, no shared base class. Each gets its own `@ExceptionHandler` method in `GlobalExceptionHandler`: `*NotFoundException` → `HttpStatus.NOT_FOUND`, `Duplicate*Exception` → `HttpStatus.CONFLICT`. `global/exception/ResourceNotFoundException.java` still exists as a generic fallback for subdomains without their own typed exception yet. New subdomains should follow this typed-exception-per-domain pattern rather than throwing `ResponseStatusException` directly from the service layer.
- **Duplicate-check-before-create**: `create<Entity>` methods check uniqueness via repository `existsBy*`/`existsById` calls *before* building the entity, throwing the domain's `Duplicate*Exception` on a hit — established on `UserServiceImpl.createUser` (`existsByUsername`/`existsByEmail`/`existsByPhone`) and carried into `UserPasswordServiceImpl.createUserPassword` (`existsById`, since `UserPasswordEntity`'s PK **is** the FK). This matters most for shared-PK/`@MapsId` entities: `JpaRepository.save()` on an entity with a non-null `@Id` does a `merge` (silent UPDATE), not an INSERT-or-fail, so without the `existsById` guard a "create" call would silently overwrite an existing row instead of erroring.
- **CRUD for a shared-PK (`@MapsId`) entity**: `UserPasswordServiceImpl` is the first CRUD service built over a derived-identity entity (see `UserPasswordEntity`'s shared-PK note above). To create one, fetch the *parent* entity via its own repository (`UserRepository.findById(request.userId())`, throwing the parent's own `UserNotFoundException` if missing) and set only the association (`.user(user)`) on the builder — **not** the raw `@Id` field (`userUid`) directly; Hibernate derives it from the association via `@MapsId` at flush time. `update`/`delete` key off `userUid` exactly like `User`'s CRUD keys off its own PK, since here the shared PK doubles as the natural identifier.
  - **No "get all" endpoint**: unlike `User`, `UserPasswordController`/`UserPasswordService`/`UserPasswordServiceImpl` deliberately have **no** `getUserPasswords()`/`getAllUserPasswords()` — a bulk-list endpoint over a credentials table (even with `raw` since dropped from `PasswordResponse`) was removed on request rather than kept for CRUD-completeness symmetry with `User`. Don't re-add it by default when extending this controller; treat per-user lookup (`GET /{userId}`) as the only supported read shape here.
  - **`PasswordResponse` excludes `raw`**: unlike the original implementation (which mirrored every entity column, `UserResponse`-style), `PasswordResponse` was edited to drop the plaintext `raw` field from the API response — it still exists on `PasswordRequest`/`UserPasswordEntity` for the [[db_raw_password_field]]-documented onboarding-phase storage reason, but the response DTO no longer echoes it back over the wire.
  - **Password-reuse check on update**: `updateUserPassword` rejects a request whose `raw` equals the currently stored `raw`, throwing `DuplicateUserPasswordException` (→ 409, same handler as the create-time duplicate check). The comparison is a plain `String.equals` on plaintext — consistent with [[db_raw_password_field]]'s standing decision that `raw` is intentionally stored unhashed during the private-onboarding phase, not something to route through a hashing/verification layer that doesn't exist yet.
- **Bean validation**: `spring-boot-starter-validation` was added to `build.gradle.kts` once `UserRequest` needed constraint annotations, so `jakarta.validation.constraints.*` and `@Valid` are now available/wired up project-wide. `UserRequest` maps its `jakarta.validation` annotations directly off `V10__auth_users.sql`'s column definitions — `@NotBlank` on every `NOT NULL`-with-no-SQL-default `String` column (`username`, `name`, `email`, `phone`), `@Size(max = n)` mirroring each `VARCHAR(n)` length (`username` 100, `name`/`email` 255, `phone` 50, `timezone` 100), and no annotation on `bio`/`avatarUrl` (`TEXT`, nullable, no length limit). Columns with a SQL `DEFAULT` (`locale`, `timezone`, `theme`, `weekStart`) stay unannotated for nullability (no `@NotNull`) since the service layer already treats a null request value as "use the DB/entity default" (see `UserServiceImpl`'s `if (request.x() != null)` guards) — only `timezone`'s `@Size` applies when a value is actually supplied. Deliberately no `@Email` on `email` — the migration only declares `VARCHAR(255) NOT NULL`, no format constraint, and the ask was to mirror the migration exactly, not add extra validation semantics. For validation to actually trigger, `UserController`'s `createUser`/`updateUser` `@RequestBody UserRequest` parameters both need `@Valid` — added alongside the DTO annotations, otherwise the constraints are inert. A failed `@Valid` currently surfaces as Spring's default `MethodArgumentNotValidException` 400 response (no custom `@ExceptionHandler` shaping it yet, consistent with the "no global `@ControllerAdvice`" note above).
- **CRUD for pure composite-PK join tables (no surrogate `id`, no `@MapsId`)**: `UserRoleServiceImpl`/`RolePermissionServiceImpl` are the first CRUD services built directly over `UserRoleEntity`/`RolePermissionEntity` (both `@EmbeddedId`-keyed join tables, see their entity notes above). Repository is `JpaRepository<Entity, EmbeddedIdClass>` (e.g. `JpaRepository<UserRoleEntity, UserRoleId>`), so `findById`/`existsById`/`delete` all take a constructed `new UserRoleId(userId, roleId)` rather than a single scalar — no custom finder methods needed. `create` resolves *both* sides via their own repositories (`UserRepository`/`RoleRepository`, throwing each side's own `*NotFoundException`) and builds via `.user(user).role(role)` — same "set the association, not the raw FK field" pattern as the `UserPassword` `@MapsId` precedent — plus an `existsById` duplicate-check before create (`DuplicateUserRoleException`/`DuplicateRolePermissionException`, → 409). Controllers expose the composite key as two path segments: `GET/DELETE /api/v1/user-roles/{userId}/{roleId}`. **Deliberately no `update` endpoint/service method on either domain** — a join table with nothing but the composite key (`RolePermissionEntity`) or the key plus an immutable `@CreationTimestamp` (`UserRoleEntity.assignedAt`) has no mutable, non-key attribute to update; the only meaningful mutations are create (assign) and delete (revoke). Don't add a no-op `update` here by default — this mirrors the `UserPassword` precedent of omitting a CRUD verb that doesn't semantically fit the entity's actual shape (there: no bulk-list; here: no update).
- **Excluding credential/secret fields from response DTOs**: extending the `PasswordResponse`-excludes-`raw` precedent, `AccountResponse` (`auth/account/`) drops `accessToken`/`refreshToken`/`idToken` (live OAuth credentials) and `RefreshTokenResponse` (`auth/refreshtoken/`) drops `secret` (a bearer credential) even though `AccountRequest`/`RefreshTokenRequest` and the entities still carry them (needed to persist). `ApiKeyResponse` (`auth/apikey/`) keeps `publicKey` (a public identifier, safe to echo back) but drops `secretHash`. None of these were explicitly requested per-field — treat "don't echo a stored secret/credential back over the API" as a standing default for any future `*Response` DTO wrapping a token/credential-bearing entity, not just a one-off.
- **Building a "reference" entity for an FK into a domain with no repository/service yet**: `ApiKeyEntity.tenant` (→ `tenant.tenants`) and `RefreshTokenEntity.widget` (→ `widget.widgets`) are real `@ManyToOne` associations (per the FK-upgrade precedent above), but neither `TenantRepository` nor `WidgetRepository` exists yet — only their entities do. `ApiKeyServiceImpl`/`RefreshTokenServiceImpl` construct a bare reference instance instead (e.g. `TenantEntity.builder().tenantId(request.tenantId()).build()`, `WidgetEntity.builder().widgetId(request.widgetId()).build()`) and set that on the association — Hibernate only needs the associated entity's `@Id` populated to write the FK column, it doesn't need the full row loaded. **Trade-off to know**: this skips existence validation (no `findById`/`orElseThrow`), so an invalid `tenantId`/`widgetId` surfaces as a raw DB-level FK-violation 500, not a clean 404 — same category of gap as the pre-`@Valid` era. Once `TenantRepository`/`WidgetRepository` exist, replace this with a real `findById(...).orElseThrow(new TenantNotFoundException(...))` lookup, the same as every other cross-domain FK in this codebase.

The caller's `user_id` comes from `CurrentPrincipalProvider.requireUser().userId()`, then `ProfileRepository.findByUserUserId(userId)` supplies the profile and organization. This intentionally inherits the known single-profile limitation: Spring Data's `Optional<ProfileEntity>` query throws on multiple matches, so multi-organization user context still needs the larger request-scoped organization-context design documented in `UserPrincipal.md`. `schedule_id` remains client-supplied and resolves through `ScheduleRepository`; the two nullable FKs `destination_calendar_id`/`destination_sheets_id` resolve through `DestinationCalendarRepository`/`DestinationSheetsRepository` only when supplied, and `update` clears them when omitted. `BusinessServiceImpl` now injects `ServiceRepository`, `BookingPolicyRepository`, `UserRepository`, `ProfileRepository`, `ScheduleRepository`, `DestinationCalendarRepository`, `DestinationSheetsRepository`, and `CurrentPrincipalProvider`.
  - **Composite-unique duplicate check, contra the entity-level note**: `ServiceEntity`'s own doc comment above says `uq_services_organization_slug` is "DB-level only, not enforced at the entity level" — that statement is about JPA/Hibernate-level annotations (no `@Column(unique = true)` equivalent for a composite key), not about service-layer business logic. `CODING_CONVENTIONS.md` still mandates a duplicate-check for every unique constraint a table declares, so `ServiceRepository` gets `existsByOrganizationOrganizationIdAndSlug(organizationId, slug)` (Spring Data nested-property traversal through the `organization` association into its `organizationId` field) and `BusinessServiceImpl.createService` calls it before building the entity, throwing `DuplicateServiceException` on a hit.

# Google OAuth2 — two mechanisms, three entry points

The server implements **two** unrelated Google integrations. Conflating them is the single easiest mistake to make in this area, so they are kept in separate packages with separate entry points.

| | Sign-In (authentication) | Delegated authorization |
|---|---|---|
| Question answered | who is this user? | may we act on their behalf? |
| Flow | ID token, posted by the browser | authorization code + redirect |
| Entry point | `POST /api/v1/auth/google` | `POST /api/v1/integrations/google/connect` |
| Google Cloud setting | Authorized **JavaScript origin** | Authorized **redirect URI** |
| Client secret used | no | yes |
| Produces | platform JWT pair | encrypted row in `integration.oauth_connections` |
| Token stored | none — verified then discarded | access + refresh, AES-256-GCM |
| Orchestration | `service/auth/DefaultGoogleSignInService` | `service/integration/DefaultGoogleConnectService` |

Both share `security/oauth/google/verifier/GoogleTokenVerifier` — the delegated flow reuses it to read the `id_token` that comes back alongside the access token, which is how the callback identifies which Google account granted consent.

## Endpoints

```text
POST   /api/v1/auth/google                              permitAll   sign-in (ID token)
POST   /api/v1/auth/google/authorize                    permitAll   one-shot: returns authorizationUrl
POST   /api/v1/auth/google/handoff                      permitAll   one-shot: code -> JWT pair
POST   /api/v1/integrations/google/connect              Bearer      returns authorizationUrl
GET    /api/v1/integrations/google/callback             permitAll   302 back to the frontend
GET    /api/v1/integrations/google/connections          Bearer      owner-scoped list
DELETE /api/v1/integrations/google/connections/{uid}    Bearer      revoke at Google, then mark REVOKED
```

## One-shot registration

### Traps specific to this flow

- **Branch on `mode == SIGN_UP_AND_CONNECT`, never on `mode == CONNECT`.** States written before the field existed deserialise with `mode = null` but still carry their `userUid`, so branching this way lets in-flight consents finish normally across a deploy. The inverse fails every consent started in the preceding 10 minutes. Covered by a regression test in `RedisOAuthStateStoreTest`.
- **Onboarding's default `redirectAfter` is `/google/complete`, not the settings page.** The callback returns *before* any session cookie exists, and the frontend gates `/dashboard` on one, so a `/dashboard/...` fallback would bounce the user to `/login` and discard the handoff code — silently, after a real consent. `DEFAULT_ONBOARDING_REDIRECT_AFTER` is separate from `DEFAULT_REDIRECT_AFTER` for this reason.
- **`finalizeOnboarding` is a separate bean, not a private method on `DefaultGoogleConnectService`.** Spring does not proxy self-invocation, so a private method would silently run with no transaction and a provisioning failure would strand a user with a Google credential and no workspace.
- **Watch the dependency direction.** `DefaultGoogleConnectService` → `GoogleOnboardingService` (the callback branch). `AuthController` therefore calls `GoogleConnectService.initiateOnboarding` **directly** rather than routing it through `GoogleOnboardingService` — the tidier-looking delegation is a constructor-injection cycle and fails at startup. `ServerApplicationTests` catches it if it is ever reintroduced.
- **A new connection with no `refresh_token` is skipped, not written.** `refresh_token` is `NOT NULL`, and on a brand-new row there is no stored value to fall back on — so the insert would abort the transaction that is *also* provisioning the account. Losing a calendar connection is recoverable; losing the registration is not. `DefaultGoogleConnectionWriter` guards this explicitly.
- **`status = ACTIVE` does not mean Calendar was granted.** Users can untick individual scopes and `persist()` sets `ACTIVE` unconditionally. Gate any "is this workspace calendar-connected?" question on the `scopes` array — raw Google URI strings, not `GoogleScope` enum names.

## Google API details that bite

- Scope URIs need `www.`: `https://www.googleapis.com/auth/calendar`, not `https://googleapis.com/auth/calendar`. The latter returns `invalid_scope` at the consent screen.
- `drive.file` is used rather than full `drive` — full Drive access triggers Google's annual CASA third-party security assessment.
- Google returns granted scopes as a **space-delimited string**, not an array. Split before writing to the `TEXT[]` column.
- Google **omits `refresh_token`** on some re-consents. The column is `NOT NULL`, so only overwrite when one actually arrives; the stored token stays valid.
- `expires_in` is **relative seconds**, not a timestamp.
- `redirect_uri` must match **byte for byte** across the authorization request, the token exchange, and the Console entry.
- `client-authentication-method: client_secret_basic` means credentials go in the HTTP Basic header **only**. Also sending them in the form body returns `invalid_client`.
- Google's `iss` claim is sometimes `accounts.google.com` (no scheme). Spring's default claim converter parses `iss` as a `java.net.URL` and throws; `GoogleOAuthConfig` overrides that one claim to stay a raw String and accepts both spellings.
- The consent screen lets users **untick individual scopes**, so granted ≠ requested. Persist what was granted.

## Token encryption

`security/crypto/TokenCipher` + `AesGcmTokenCipher`: AES-256-GCM, fresh 12-byte IV per encryption prepended to the ciphertext, 128-bit tag, Base64 output. Keys come from `security.token-encryption.{current-version,keys}` and are validated at startup — wrong length or bad Base64 fails the boot, not the first request.

`decrypt(ciphertext, keyVersion)` takes the version as a parameter rather than reading it from the payload, which is what makes `oauth_connections.token_key_version` functional: rotation is a config change (add key 2, set current to 2), existing rows keep decrypting with the version recorded against them, and no re-encryption sweep is needed.

`TokenEncryptionException` is deliberately **not** wired into `GlobalExceptionHandler` — a decrypt failure is a server fault and cipher details must not reach a client, so it falls through to a generic 500.
