## 1. Purpose

This document defines the standard for generating table-level database documentation.

AI agents MUST read and follow this convention before generating or updating documentation for any database table.

The purpose of table-level documentation is to explain the **semantic contract and operational meaning** of a table.

Table documentation MUST NOT duplicate the database design documentation unnecessarily.

The database schema/DDL already defines:

- Columns
    
- Data types
    
- Primary keys
    
- Foreign keys
    
- Indexes
    
- Constraints
    
- Default values
    

Table documentation exists to explain what those structures **mean**, how the table is **used**, and what rules engineers must understand when interacting with it.

---

# 2. Documentation Principles

## 2.1 Document Meaning, Not Structure

Documentation MUST explain the meaning of the table rather than restating its DDL.

Bad:

> `status` is a VARCHAR column containing the status.

Good:

> `status` determines whether the resource is currently eligible to participate in booking operations.

The schema describes **what exists**.

The documentation describes **what it means**.

---

## 2.2 Define the Meaning of One Row

Every table MUST explicitly define its row semantics.

The agent MUST answer:

> "What does exactly one row represent?"

Examples:

> Each row represents one bookable service offered by an organization.

> Each row represents one role assignment between a user and an organization.

> Each row represents one auditable event generated by an actor.

Avoid vague descriptions such as:

> Stores users.

> Contains booking information.

> Stores resource data.

The row semantics should be precise enough that an engineer can determine whether a new real-world occurrence requires a **new row** or an **update to an existing row**.

---

## 2.3 Explain Invariants

Documentation MUST describe important invariants that are not sufficiently obvious from the schema.

An invariant is a condition that must remain true during the lifetime of the data.

Examples:

- A user cannot have the same role assigned twice within the same organization.
    
- A booking must belong to exactly one service.
    
- Posted ledger entries cannot be modified.
    
- Audit events are append-only.
    
- A revoked API key cannot become active again.
    

Do not document trivial constraints merely because they exist in SQL.

---

## 2.4 Explain Lifecycle

When a table has meaningful state transitions or lifecycle behavior, documentation MUST explain them.

The agent should describe:

- How records are created
    
- Important state transitions
    
- How records are cancelled or revoked
    
- Whether records can be deleted
    
- Whether records are retained indefinitely
    
- Whether records become inactive rather than deleted
    

The documentation should describe **semantic lifecycle**, not implementation details.

---

## 2.5 Explain Ownership and Boundaries

The documentation MUST identify the logical owner of the table.

Where applicable, explain:

- Domain ownership
    
- Module ownership
    
- Tenant boundary
    
- Organization boundary
    
- User boundary
    
- Resource boundary
    

For multi-tenant systems, the documentation MUST explicitly identify the relevant isolation boundary when applicable.

Example:

> Records are organization-scoped. Application queries must not expose records belonging to another organization.

---

## 2.6 Explain Usage Rules

If the table has restrictions on how application code should interact with it, document those restrictions.

Examples:

- Append-only
    
- No physical deletion
    
- State changes must go through a domain service
    
- Direct writes from controllers are prohibited
    
- Records must be created through a specific application workflow
    
- Updates to historical records are prohibited
    

Do not invent such rules.

Only document rules that can be established from the available schema, source code, architecture documentation, or existing project conventions.

---

## 2.7 Avoid Speculation

AI agents MUST NOT invent business rules.

If a rule cannot be established confidently from available project information:

- Do not present it as fact.
    
- Do not infer business behavior from a column name alone.
    
- Do not fabricate lifecycle transitions.
    
- Do not fabricate authorization rules.
    
- Do not fabricate retention requirements.
    

When necessary, use:

> **Undetermined:** The available database definition does not establish whether historical records may be physically deleted.

Agents MAY omit uncertain information rather than documenting speculation.

---

## 2.8 Prefer Concise Semantic Documentation

Documentation should be detailed enough to be useful but should not become an essay.

A normal table document should generally be between:

- 150–500 words for a simple table
    
- 300–800 words for a normal domain table
    
- 500–1,000+ words only for complex tables such as bookings, audit events, authorization structures, or heavily stateful entities
    

Do not add content merely to make the document longer.

---

# 3. Table Variants

Not all tables should use exactly the same documentation emphasis.

The agent MUST classify each table into one primary variant.

The available variants are:

1. `ENTITY`
    
2. `ASSOCIATION`
    
3. `TRANSACTION`
    
4. `EVENT`
    
5. `AUDIT`
    
6. `CONFIGURATION`
    
7. `REFERENCE`
    
8. `STATE`
    
9. `HISTORY`
    
10. `SYSTEM`
    

A table MAY have secondary characteristics, but exactly one primary variant SHOULD be selected.

---

## 3.1 ENTITY

Use for tables representing a persistent business or domain entity.

Examples:

- `users`
    
- `services`
    
- `resources`
    
- `customers`
    
- `organizations`
    

Emphasize:

- Row semantics
    
- Ownership
    
- Lifecycle
    
- Relationships
    
- Invariants
    
- Important fields
    

---

## 3.2 ASSOCIATION

Use for junction/relationship tables whose primary purpose is associating two or more entities.

Examples:

- `user_roles`
    
- `role_permissions`
    
- `resource_assignments`
    
- `memberships`
    

Emphasize:

- What relationship one row represents
    
- Participating entities
    
- Cardinality
    
- Uniqueness of the relationship
    
- Lifecycle of the association
    
- Authorization implications where established
    

Example row semantics:

> Each row represents one role assignment for one user within one organization.

Do not treat an association table like a normal business entity unless it has independent domain semantics.

---

## 3.3 TRANSACTION

Use for tables representing business operations, transactions, or operational records.

Examples:

- `bookings`
    
- `payments`
    
- `business_transactions`
    
- `orders`
    

Emphasize:

- Transaction semantics
    
- Lifecycle
    
- State transitions
    
- Idempotency
    
- Invariants
    
- Immutability requirements
    
- Related entities
    

---

## 3.4 EVENT

Use for tables representing domain or system events.

Examples:

- domain events
    
- integration events
    
- notification events
    
- webhook events
    

Emphasize:

- What event one row represents
    
- Event producer
    
- Event consumer, if known
    
- Event lifecycle
    
- Ordering semantics, if known
    
- Idempotency
    
- Immutability
    
- Processing status
    

Do not invent event delivery guarantees.

---

## 3.5 AUDIT

Use for audit/security records.

Examples:

- `audit_events`
    
- `audit_logs`
    
- `audit_changes`
    

Emphasize:

- What action/event is recorded
    
- Actor semantics
    
- Resource semantics
    
- Immutability
    
- Append-only behavior
    
- Correlation/request/trace information
    
- Security significance
    
- Retention rules, if established
    

Audit tables SHOULD explicitly state whether they are operational source-of-truth data or historical evidence.

---

## 3.6 CONFIGURATION

Use for tables storing configurable behavior or policies.

Examples:

- `booking_policies`
    
- application settings
    
- tenant configuration
    
- service configuration
    

Emphasize:

- What behavior the configuration controls
    
- Scope of the configuration
    
- Precedence rules, if known
    
- Lifecycle
    
- Defaults
    
- Validation/invariants
    
- Which domain consumes the configuration
    

---

## 3.7 REFERENCE

Use for relatively stable reference/catalog data.

Examples:

- `resource_types`
    
- country tables
    
- currency tables
    
- system-defined categories
    

Emphasize:

- What the reference data represents
    
- Who owns it
    
- Whether application code or administrators may modify it
    
- Expected stability
    
- Relationship to dependent tables
    

---

## 3.8 STATE

Use when the table primarily represents current state rather than historical events.

Examples:

- session state
    
- synchronization state
    
- processing state
    

Emphasize:

- State represented by each row
    
- State transitions
    
- Current-state semantics
    
- Concurrency considerations if established
    
- Expiration
    
- Cleanup behavior
    

---

## 3.9 HISTORY

Use for tables whose primary purpose is historical records.

Examples:

- historical snapshots
    
- change history
    
- archived records
    

Emphasize:

- What historical fact one row represents
    
- Source record
    
- Temporal semantics
    
- Immutability
    
- Retention
    
- Ordering/versioning
    

---

## 3.10 SYSTEM

Use for infrastructure/internal persistence tables.

Examples:

- migration metadata
    
- idempotency records
    
- locks
    
- job execution state
    
- internal synchronization metadata
    

Emphasize:

- Infrastructure purpose
    
- Owning subsystem
    
- Lifecycle
    
- Cleanup behavior
    
- Concurrency/consistency semantics
    
- Restrictions on direct modification
    

---

# 4. Required Metadata

Every table document MUST contain the following metadata.

|Field|Required|Description|
|---|--:|---|
|`Table`|YES|Fully qualified table name|
|`Variant`|YES|Primary table variant|
|`Purpose`|YES|Concise purpose|
|`Fields`|YES|Every column, with its type and a brief semantic note|
|`Row Semantics`|YES|Meaning of one row|
|`Ownership`|YES|Logical domain/module owner|
|`Scope`|YES|Tenant/org/user/global/etc.|
|`Lifecycle`|YES|Lifecycle summary|
|`Invariants`|YES|Important conditions that must remain true|
|`Relationships`|YES|Semantically important relationships|
|`Usage Rules`|YES|Rules governing application interaction|

A field may contain:

> None identified.

when the concept genuinely does not apply.

Agents MUST NOT fabricate content merely to fill a required field.

---

# 5. Optional Metadata

The following sections SHOULD be included when applicable:

- Important Fields
    
- State Model
    
- Immutability
    
- Audit Behavior
    
- Security Considerations
    
- Retention
    
- Concurrency
    
- Idempotency
    
- Processing Semantics
    
- Data Sensitivity
    
- Examples
    
- Related Tables
    

Do not include optional sections when they provide no meaningful information.

# 7. Field-Specific Writing Rules

## 7.1 Purpose

Write **1–3 sentences**.

The purpose MUST answer:

> Why does this table exist?

Do not describe individual columns.

Bad:

> Stores the user ID, username, email, and account status.

Good:

> Stores the platform identities used to authenticate and identify users across the application.

---

## 7.2 Fields

List **every** column in the table, in schema order, as a `Field | Type | Description` table.

The `Type` column is a short type hint (e.g. `VARCHAR(100)`, `UUID`, `JSONB`, `TIMESTAMPTZ`), not a full DDL reproduction — omit lengths/precision when not meaningful, and never restate constraints, defaults, or indexes here. See section 11 for how this reconciles with "Do Not Duplicate DDL."

The `Description` column is one short phrase per field: what the field means, not what its type is. Every field gets an entry, including ones that are also called out in `Important Fields` later — this section is the exhaustive reference; `Important Fields` is the selective, explained-in-depth subset.

Bad:

> `status` — VARCHAR(50).

Good:

> `status` — Determines whether the resource is currently eligible to participate in booking operations.

---

## 7.3 Row Semantics

Write **one precise statement**, optionally followed by one clarification.

Use the structure:

> Each row represents `<one business/system concept>`.

Examples:

> Each row represents one customer belonging to a tenant.

> Each row represents one assignment of a resource to an organization membership.

> Each row represents one booking request and its resulting operational state.

This is the most important field in the document.

---

## 7.4 Ownership

Identify who conceptually owns the data.

Possible ownership levels include:

```text
Platform
Domain
Module
Subsystem
Integration
Infrastructure
```

If ownership cannot be determined, state:

> Ownership is not explicitly established by the available documentation.

Do not infer ownership solely from the schema name.

---

## 7.5 Scope

Explicitly identify the isolation boundary.

Allowed values include:

```text
GLOBAL
TENANT
ORGANIZATION
USER
MEMBERSHIP
RESOURCE
SERVICE
SESSION
SYSTEM
UNKNOWN
```

If multiple scopes apply, explain them.

Example:

> **Scope:** Tenant → Organization → Service.

The agent MUST distinguish **data ownership** from **authorization scope** when they differ.

---

## 7.6 Lifecycle

Describe semantic lifecycle rather than CRUD operations.

Good:

> Records are created when a customer successfully creates a booking. A booking may transition between pending, accepted, rejected, and cancelled states. Historical bookings are retained after cancellation.

Bad:

> The application inserts, updates, and deletes rows.

---

## 7.7 Invariants

List only meaningful invariants.

Good:

- A membership belongs to exactly one organization.
    
- A user may have only one membership for the same organization.
    
- Revoked API keys cannot be used for authentication.
    

Avoid obvious statements such as:

- `id` must be unique.
    

unless the uniqueness has unusual domain significance.

---

## 7.8 Relationships

Describe **semantic relationships**, not merely foreign keys.

Bad:

> `service_id` references `services.id`.

Good:

> **Service:** Each booking is created against a specific service, which determines the booking configuration applicable to the operation.

The database schema remains the authoritative source for exact FK definitions.

---

## 7.9 Usage Rules

Describe how engineers are expected to interact with the table.

Examples:

- Writes must occur through the domain/application service.
    
- Records are append-only.
    
- Physical deletion is prohibited.
    
- Queries must be tenant-scoped.
    
- State transitions must be validated before persistence.
    
- Direct modification by administrative SQL is prohibited.
    

Only document rules supported by project evidence.

---

## 7.10 Important Fields

Include only fields whose semantic meaning is not obvious from their names.

Prioritize:

- State fields
    
- Scope identifiers
    
- Ownership identifiers
    
- Security fields
    
- Version fields
    
- Temporal fields
    
- Polymorphic identifiers
    
- Configuration fields
    
- Fields with unusual semantics
    

Do not document every column.

---

# 8. Special Semantic Sections

These sections should be used when the table has characteristics that deserve explicit treatment.

## Immutability

Use when records cannot or should not be modified.

Example:

> Records are append-only after creation. Existing audit events must not be modified or deleted through normal application operations.

---

## Audit Behavior

Explain:

- What operation generates an audit record
    
- What actor is recorded
    
- What resource is associated
    
- Whether before/after state is captured
    
- Whether the record is immutable
    

Do not duplicate the entire audit architecture.

---

## Security Considerations

Document:

- Sensitive information
    
- Authorization boundaries
    
- Security-critical state
    
- Credential-related semantics
    
- Cross-tenant isolation
    
- Security audit requirements
    

Never expose secrets or credentials in documentation.

---

## Retention

Use when retention behavior is explicitly defined.

Document:

- Retention period
    
- Archival behavior
    
- Deletion policy
    
- Legal/compliance requirements if established
    

Never invent retention periods.

---

## Concurrency / Idempotency

Use when the table participates in concurrency control or duplicate-operation prevention.

Examples:

- Idempotency keys
    
- Version columns
    
- Optimistic locking
    
- Unique operation identifiers
    
- Distributed locks
    

Explain the semantic purpose, not the implementation unless necessary.

---

# 9. Evidence Rules for AI Agents

When generating documentation, agents MUST prioritize evidence in this order:

1. Database schema / DDL
    
2. Database migration files
    
3. Domain/application code
    
4. Authorization/security code
    
5. Existing architecture documentation
    
6. Existing table documentation
    
7. Tests
    
8. Naming conventions
    
9. Reasonable inference
    

Higher-priority evidence overrides lower-priority inference.

Agents MUST distinguish between:

### Explicitly established

> The schema contains a unique constraint on `(tenant_id, email)`.

### Strongly implied

> The table appears to be tenant-scoped because every record contains `tenant_id` and application queries consistently filter by it.

### Unknown

> The available project information does not establish whether records are retained indefinitely.

Agents MUST NOT convert an inference into an established business rule.

---

# 10. Schema Is the Source of Truth

The generated documentation MUST NOT contradict the actual database schema.

If documentation and schema disagree:

1. Treat the database schema as authoritative for structural facts.
    
2. Flag the semantic discrepancy.
    
3. Do not silently rewrite the schema's meaning.
    

For example, if documentation says a relationship is one-to-one but the schema permits many records, the agent should report the inconsistency rather than documenting the relationship as one-to-one.

---

# 11. Do Not Duplicate DDL

The following information SHOULD NOT normally be reproduced in table documentation:

- Complete column lists
    
- Complete data types
    
- Complete indexes
    
- Complete FK definitions
    
- Complete constraints
    
- Full `CREATE TABLE` statements
    

Instead, refer engineers to the schema or migration when structural details are required.

Example:

> Structural definitions, including constraints, indexes, and foreign keys, are defined by the database migration.

**Exception:** the required `Fields` section (§6, §7.2) does enumerate every column, by design — that is what makes it exhaustive rather than the selective `Important Fields` section. This exception is narrow: a short type hint and a one-line semantic note per field, nothing more. It does not extend to reproducing full constraint syntax, default-value expressions, index definitions, or FK `REFERENCES`/`ON DELETE` clauses — those remain out of scope everywhere in the document, `Fields` included.

---

# 12. Documentation Quality Standard

Before finalizing a table document, the agent MUST verify:

### Identity

-  Fully qualified table name is correct.
    
-  Primary table variant is identified.
    

### Semantics

-  Purpose explains why the table exists.
    
-  Row Semantics clearly defines one row.
    
-  Ownership is identified.
    
-  Scope is identified.
    

### Behavior

-  Lifecycle is documented.
    
-  Important invariants are documented.
    
-  Important relationships are explained semantically.
    
-  Usage rules are documented when applicable.
    

### Accuracy

-  No unsupported business rules were invented.
    
-  Documentation does not contradict the schema.
    
-  Structural details are not unnecessarily duplicated.
    
-  Optional sections are included only when relevant.
    

### Security

-  Tenant/organization isolation is documented where applicable.
    
-  Sensitive data considerations are documented where applicable.
    
-  Audit/immutability requirements are documented where applicable.
    

---

# 13. Recommended Writing Style

Table documentation MUST be:

- Technical
    
- Precise
    
- Declarative
    
- Concise
    
- Domain-oriented
    
- Implementation-aware where necessary
    

Prefer:

> Each row represents one active membership between a user and an organization.

Over:

> This table is basically used to keep track of memberships that users have in organizations.

Prefer:

> Records are append-only after creation.

Over:

> We generally don't want developers to modify these records.

Use consistent terminology throughout the project.

If the domain calls the concept a **booking**, do not alternate between:

- appointment
    
- reservation
    
- booking
    
- schedule entry
    

unless those are actually distinct concepts.

# 14. Example: Normal Entity

```markdown
# `core.services`

> **Variant:** `ENTITY`

## Purpose

Stores the bookable services offered by organizations.

## Fields

| Field | Type | Description |
|---|---|---|
| `id` | `BIGSERIAL` | Internal surrogate primary key. |
| `title` | `VARCHAR(255)` | Customer-facing service name. |
| `slug` | `VARCHAR(255)` | URL-safe identifier, unique per organization. |
| `description` | `TEXT` | Optional customer-facing description. |
| `interface_language` | `public.locale` | Language the booking flow is presented in for this service. |
| `location` | `TEXT` | Optional service location. |
| `user_id` | `BIGINT` | The user who administers this service. |
| `profile_id` | `BIGINT` | The staff profile presented to customers for this service. |
| `organization_id` | `BIGINT` | The organization that owns this service. |
| `schedule_id` | `BIGINT` | The availability schedule this service books against. |
| `period_type` | `VARCHAR(50)` | Booking period model (e.g. fixed-duration vs. unlimited). |
| `timezone` | `VARCHAR(100)` | Timezone used to interpret this service's availability. |
| `min_price` / `max_price` | `NUMERIC(10,2)` | Optional price range shown to customers. |
| `currency` | `public.currency` | Currency the price range is denominated in. |
| `disable_cancelling` / `disable_rescheduling` | `BOOLEAN` | Whether customers may cancel/reschedule their own bookings. |
| `success_redirect_url` | `TEXT` | Optional post-booking redirect target. |
| `is_instant_service` | `BOOLEAN` | Whether this service skips the standard scheduling flow. |
| `max_active_booking_per_booker` | `INTEGER` | Optional cap on concurrent active bookings per customer. |
| `metadata` | `JSONB` | Free-form, application-defined data. |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | Row creation/last-modified timestamps. |

## Row Semantics

Each row represents one bookable service that can be presented to customers and used as the target of a booking operation.

## Ownership

- **Domain:** Core / Booking
- **Module:** Service Management
- **Scope:** Organization

## Lifecycle

A service is created by an authorized organization member and may subsequently be updated or disabled. Disabling a service prevents it from participating in new booking operations while preserving existing historical relationships.

## Invariants

- A service belongs to a valid organization.
- A service must have a valid booking configuration before it can accept bookings.
- A disabled service must not accept new bookings.

## Relationships

- **Organization:** The organization owns the service.
- **Booking:** Bookings reference the service being requested.
- **Schedule:** The service uses its associated schedule to determine availability.
- **Resource:** A service may be associated with bookable resources.

## Usage Rules

- Service creation and modification must occur through authorized service-management operations.
- Booking operations must validate that the service is currently eligible for booking.

## Important Fields

- `status` — Determines whether the service is currently available for operational use.
- `schedule_id` — Associates the service with the availability schedule used during booking.
- `organization_id` — Establishes the service's organizational ownership boundary.
```

# 15. Example: Association Table

```markdown
# `auth.user_roles`

> **Variant:** `ASSOCIATION`

## Purpose

Associates users with roles for authorization purposes.

## Fields

| Field | Type | Description |
|---|---|---|
| `user_id` | `BIGINT` | Part of the composite primary key; the user receiving the role. |
| `role_id` | `BIGINT` | Part of the composite primary key; the role being assigned. |
| `assigned_at` | `TIMESTAMPTZ` | When the assignment was created. Immutable — this table has no `updated_at`. |

## Row Semantics

Each row represents one role assignment for one user.

## Ownership

- **Domain:** Authorization
- **Module:** Identity & Access Management
- **Scope:** Depends on the associated role and authorization model

## Lifecycle

A row is created when a role is granted to a user and removed or otherwise invalidated when the role assignment is revoked.

## Invariants

- A user-role combination must not be duplicated.
- Both the referenced user and role must exist.
- A revoked role assignment must not grant authorization.

## Relationships

- **User:** Identifies the principal receiving the role.
- **Role:** Identifies the authorization role being assigned.

## Usage Rules

- Role assignments must be created through authorized authorization-management operations.
- Authorization checks must evaluate the current assignment state rather than assuming historical assignments remain valid.
```

# 16. Example: Audit Table

```markdown
# `audit.audit_events`

> **Variant:** `AUDIT`

## Purpose

Records security and operational events generated by application actors and system components.

## Fields

| Field | Type | Description |
|---|---|---|
| `id` | `BIGSERIAL` | Internal surrogate primary key. |
| `uid` | `UUID` | Stable, externally-safe identifier for this event. |
| `tenant_id` / `organization_id` | `BIGINT` | Optional tenant/organization context, when the event originated within one. |
| `actor_id` | `BIGINT` | The actor responsible for the event. |
| `correlation_id` / `request_id` / `trace_id` | `VARCHAR(255)` | Optional identifiers linking this event to the originating request/trace. |
| `event_domain` | `audit.event_domain` | Which platform domain the event occurred in. |
| `event_type` | `audit.event_type` | The kind of entity the event concerns. |
| `action` | `audit.audit_action` | The action that occurred. |
| `severity` | `audit.severity` | Security/operational severity classification. |
| `status` | `audit.audit_status` | Outcome of the audited operation. |
| `context` | `JSONB` | Optional free-form contextual data. |
| `event_version` | `INTEGER` | Schema version of this event's payload shape. |
| `occurred_at` | `TIMESTAMPTZ` | When the audited operation occurred. |
| `created_at` | `TIMESTAMPTZ` | When this audit row was written. |

## Row Semantics

Each row represents one auditable event associated with an operation performed by an identified actor.

## Ownership

- **Domain:** Audit
- **Module:** Audit & Compliance
- **Scope:** Tenant or platform, depending on the originating operation

## Lifecycle

Audit events are created when an auditable operation occurs. Existing events are retained as historical records and are not modified as part of normal application operation.

## Invariants

- Each event must have a valid event identity.
- The event must identify its originating actor when actor information is available.
- Existing audit events must remain immutable.
- Audit records must not become the operational source of truth for the business operation they describe.

## Relationships

- **Actor:** Identifies the principal or system component responsible for the event.
- **Resource:** Identifies the resource affected by the event.
- **Tenant:** Establishes the tenant context when the event is tenant-scoped.

## Usage Rules

- Audit events are append-only.
- Application code must not modify existing audit events.
- Audit events should be generated as part of the operation being audited rather than manually reconstructed later.

## Immutability

Audit events are immutable after creation.

## Audit Behavior

This table is itself part of the audit subsystem. Its records represent historical evidence rather than mutable operational state.

## Security Considerations

Audit records may contain security-sensitive context such as actor identity, request metadata, and resource information. Access must therefore be restricted according to the project's audit authorization policy.
```

---

# 17. Agent Generation Procedure

When asked to generate documentation for a table, the agent SHOULD follow this process:

```text
1. Identify the fully qualified table name.

2. Inspect the schema definition.

3. Identify the table's primary semantic purpose.

4. Determine what exactly one row represents.

5. Classify the table variant.

6. Identify ownership and scope.

7. Inspect foreign keys and determine semantic relationships.

8. Inspect constraints and identify meaningful invariants.

9. Inspect application/domain code for lifecycle behavior.

10. Inspect authorization/security behavior where relevant.

11. Determine whether immutability, audit, retention,
    concurrency, or idempotency semantics apply.

12. Generate the standard document.

13. Remove sections that are not applicable.

14. Validate the document against the actual schema.

15. Identify uncertainty rather than inventing missing information.
```

---

# 18. Final Principle

The agent should think about table documentation as answering:

> **"What contract does this table represent to the rest of the system?"**

It should **not** think:

> "How can I describe every column in this table?"

The resulting documentation should allow an engineer who has never seen the table before to understand:

```text
What is this?
      ↓
What does one row mean?
      ↓
Who owns it?
      ↓
What is its scope?
      ↓
How does it live?
      ↓
What must always be true?
      ↓
What does it relate to?
      ↓
How may the application interact with it?
      ↓
Are there security / audit / immutability constraints?
```

That is the standard for table-level documentation.
